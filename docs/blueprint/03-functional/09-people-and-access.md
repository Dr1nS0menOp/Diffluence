# 03.9: People and access

## 9.1 Accounts and login

- **ACC-001** · built · A local account has an e-mail address, a display name and a password hashed with Argon2id.
- **ACC-002** · built · Login is by password, by password with an authenticator code, by passkey, or by single sign-on with OpenID Connect.
- **ACC-003** · built · The login page shows only the methods that are configured.
- **ACC-004** · built · Failed logins are rate limited, and the wording never reveals whether an account exists.
- **ACC-005** · built · A person changes their own password with the current one. All other sessions then end.
- **ACC-006** · built · A person sees their sessions, and can end any of them.
- **ACC-007** · built · A person sets up an authenticator app and receives 10 recovery codes, each usable once.
- **ACC-008** · built · A person registers, lists and removes passkeys.
- **ACC-009** · built · An administrator resets a password or the second factor of a person, and it is audited.
- **ACC-010** · built · The first administrator is created from the command line, or on the setup screen of a new install with the one-time code from the server's log (spec 038).
- **ACC-011** · built · **Forgot password:** a person asks for a link by e-mail, which works once and expires within an hour. It works only when e-mail is configured, and never for accounts of an identity provider.
- **ACC-012** · built · **Invitation:** an administrator invites by e-mail. The person chooses their own password and name, and the link expires.
- **ACC-013** · built · **Self sign-up:** optional, limited to e-mail domains on a list. Off by default.
- **ACC-014** · built · **Password rules:** a minimum length, with a check against lists of leaked passwords that works offline, and no rules that force odd characters.
- **ACC-015** · built · An administrator can require a second factor for all members, or for administrators only.
- **ACC-016** · built · A session ends after a configurable idle time, with a warning first, and the draft stays safe.
- **ACC-017** · built · A person sees recent logins with place and device, and is told by e-mail of a login from a new device.
- **ACC-018** · built · Single sign-on links accounts on stable ids, and never takes over a local account by e-mail alone.
- **ACC-019** · built · **Personal API tokens:** a person creates tokens for scripts, with a name, an expiry and a limited scope. Tokens are shown once, stored hashed, and can be revoked. An administrator can turn the feature off.
- **ACC-074** · new · Beyond ACC-006, the sessions screen is a table of the person's running sessions, the most recently active first, with the columns device, program, network address, last active and action. It has no place, no first-seen date, no checkboxes, no row menu and no count, and it never lists a session older than the absolute limit of SEC-176.
- **ACC-075** · new · In each session row the device cell shows an icon for a computer or a phone with the kind of device, and the operating system and its version muted under it; the program cell shows the browser or app with its version muted under it. The network address shows in full, and last active is relative time, which reads as now for the session in use (NAV-078).
- **ACC-076** · new · The session in use is marked in its action cell by a status mark in words with the success colour, and has no button to end it. Every other row has a normal button that ends that session at once (SEC-174).
- **ACC-077** · new · A button at the end of the sessions heading's line, its end edge level with the end of the table, ends all other sessions at once. It takes the danger style and asks first, repeating the action on its confirming button, which completes SEC-177.
- **ACC-078** · new · Under the heading of the sessions screen, one sentence explains the list and what to do after losing a device, with a link to the user guide. A sub-heading then names the table, and the largest gap of the screen lies between the explanation and the list.
- **ACC-079** · new · Beyond ACC-019, the tokens screen lists the person's personal API tokens in a table with the columns name, scope, created, expires, last used and action, newest first. The scope column lets a person tell a read token from a write token (SEC-227); there is no sort, filter, search, selection, paging or count.
- **ACC-080** · new · A long token name wraps over several lines instead of being cut off, and the other cells stay centred against it. Created and expires are dates written as day, short month and year, and last used is relative time, or says in words that the token was never used.
- **ACC-081** · new · A token row offers only Revoke: a token cannot be renamed, given a new end date, renewed or shown again after it was made, and its secret never appears in the list.
- **ACC-082** · new · A person holds at most a set number of live personal tokens at once, and the explanation above the list states that number. At the limit, creating a token says why it cannot (the number needs its own study).
- **ACC-083** · new · Above the token list, one sentence says that a token acts as the person and must be kept as safely as a password, with a link to the user guide, and a row of compact buttons follows: Create token, the one primary action, then Revoke all tokens. There is one Create, which asks for the scope in its form (spec 013 F6).
- **ACC-084** · new · **Revoke all tokens** ends every personal token of the person in one action. It takes the danger style, a confirmation says how many tokens will stop working and repeats the action on its button, and each token is audited as revoked, as a single revoke is.
- **ACC-085** · new · The tables of the tokens and sessions screens follow NAV-157, with airy rows of up to two lines whose second line is muted (changes the design standard, decided 2026-11-14).
- **ACC-086** · new · A person with a local account changes their own e-mail address in Your account. The change asks for the password or a passkey again (ADM-005), takes effect only after the person follows a link mailed to the new address, and the old address is told of the change (SEC-192); accounts link on stable ids, so no link changes with it (SEC-143).
- **ACC-087** · new · Until that link is followed, the old address stays the one for login and for a password reset, and the link works once and expires. Without mail set up, Your account offers no change and only an administrator changes an address, with a fresh proof of identity and audited (how long the link lasts, and what a reset does to a waiting change, need their own study).
- **ACC-088** · later · The account menu offers a way to switch to another account of the same person on this instance, such as a separate administrator account, just above Log out. Switching ends the current session and opens the login page, and an open draft stays safe (whether two sessions at once are wanted, against the rules of 06.2, needs its own study).
- **ACC-089** · later · Beyond ACC-013, the list of e-mail domains for self sign-up is a table that can be searched by domain, with a count line, Add domain as its one primary action, and per domain the number of accounts with an address on it and a row menu. Proving that a domain is the organisation's and claiming the accounts on it are left out, because the instance owns every account it holds (ADR-008).
- **ACC-090** · later · An administrator makes **login policies**. Each policy holds for chosen groups or people, a default policy holds for everyone else, one for local accounts and one for accounts of the identity provider, so every account falls under at least one policy.
- **ACC-091** · later · A login policy sets whether a second factor is required, how long a session may stay unused, how long it may last at most, whether its people may make personal API tokens and the longest life of such a token, and whether its people sign in with a local password or only through the identity provider (ACC-100).
- **ACC-092** · later · When login policies arrive, the rules of ACC-015, ACC-016 and ACC-019 become the default policies and the requirement for administrators becomes a policy for administrators, so nobody gains or loses anything. A policy for chosen groups or people can only be stricter than the default, and a person under several policies gets the strictest value of each setting.
- **ACC-093** · later · A login policy offers no password strength levels, no forced password expiry, no way to block passkeys and no session without an absolute limit: the minimum length and the blocklist stay one rule for everyone (SEC-102, SEC-104), people stay pushed towards passkeys (ADR-026, SEC-160), and the defaults stay 8 hours unused and 7 days at most (SEC-176, ADR-029).
- **ACC-094** · later · The default policy for accounts of the identity provider says in words, in place of a value, that the provider handles their password and their second factor, since these accounts are exempt from the second-factor rule (spec 013 F5).
- **ACC-095** · later · A new login policy can start with a few chosen people, to try it before it reaches a group. A trial policy with nobody in it shows zero people.
- **ACC-096** · later · Making, changing or removing a login policy, and changing who falls under it, asks for the password or a passkey again and is audited with before and after (SEC-603, SEC-605). How a change reaches sessions that are running, and the cost of finding a person's policy on each request (ARC-238), need their own study.
- **ACC-097** · later · The login policies screen has Add policy, its one primary action, at the end of the title line, an introduction of one sentence with a link to the user guide, a bold count line of policies, and then the policies as cards, two per row of equal width and height, and one per row on a narrow screen (changes the design standard, decided 2026-11-14).
- **ACC-098** · later · A policy card shows its name in bold with a neutral outlined mark on a default policy, and Edit, a normal button in the card's top end corner and its only action. Under them come the number of people as the largest figure with a wider gap below it, where those accounts come from, and the settings as small muted bold labels over plain values, related settings paired in two columns on the start half of the card.
- **ACC-099** · later · In a policy card, a value the identity provider decides is muted words that say so, a strict setting that is on shows as a status mark in words with the success colour, and values are in sentence case. Edit opens the policy's form (that form needs its own study).
- **ACC-100** · new · An administrator can require that accounts of the identity provider sign in only through it, so that disabling the person at the provider closes every way in. Such an account then has no password and no passkey here, while local accounts keep every way in.
- **ACC-101** · new · Turning the rule of ACC-100 on or off asks for the password or a passkey again and is audited, and while it is on Your account shows a notice in place of the password and passkeys of such an account (ACC-110). Passkeys such accounts already hold, and step-up through the provider (SEC-150), need their own study.

## 9.2 Profile and preferences

- **ACC-020** · built · A profile screen shows the picture, name, job title, department, location, local time, e-mail and a short text, within what the viewer may see.
- **ACC-021** · built · It lists recent pages, spaces and blog posts by the person, filtered for the viewer.
- **ACC-022** · built · A person uploads and crops a profile picture. Without one, the initials show on a tint chosen from the name.
- **ACC-023** · built · A person chooses which fields are visible to others. An identity provider can fill and lock some fields.
- **ACC-024** · partly · **Your account** holds security, sessions and passkeys. Built: profile, preferences, security, tokens, data. Still open: notifications and watches (wave C).
- **ACC-025** · partly · **Preferences:** language, time zone, date format, theme, keyboard shortcuts on or off, hover cards on or off, typing replacements on or off, toolbar pinned or not, editor width. Built: language, time zone, date format, first day, theme, shortcuts, cards. Still open: typing replacements, toolbar pinned, editor width.
- **ACC-026** · built · Preferences are stored with the account, not in the browser, so they follow a person.
- **ACC-027** · built · A person can download all their personal data, and ask an administrator for removal, for GDPR requests.
- **ACC-028** · built · A disabled person's name stays on their work, marked as no longer active. An administrator can anonymise the name for a GDPR removal, with the content untouched.
- **ACC-102** · new · **Your account** has a bar of its own in place of the top bar: our logo and the words Your account at the start, then its sections as a row of text tabs, and help and the account menu at the end, with no search, bell or Create and a thin line under it (changes the design standard, decided 2026-11-14).
- **ACC-103** · new · The tabs of Your account are muted text; the selected tab is accent text with a bar on the lower edge of the bar and is marked as current for screen readers, and a tab under the pointer or focus gets a tint. Each tab has an address of its own, and a tab stays selected on the screens below it.
- **ACC-104** · new · Under its bar, every screen of Your account is one narrow column of fixed width centred in the window, with wide empty margins and no sidebar, breadcrumbs, back link, footer or save bar, and the page scrolls as a whole (changes the design standard, decided 2026-11-14).
- **ACC-105** · new · The sections of Your account come in this order: Profile and visibility, E-mail, Security, Privacy, Preferences, Connected apps once apps exist (ACC-122), Link preferences, Notifications, Watches. Tokens and Sessions are no longer sections of their own but screens below Security (ACC-108).
- **ACC-106** · new · A section of Your account shows its title, a notice where one applies (ACC-110), then its parts, each with a bold heading close to its content and clearly larger gaps between parts than inside them. A link to the user guide ends its sentence with a mark that it leaves the instance, while a link that opens another screen of Your account stands alone on its own line without that mark.
- **ACC-107** · new · Each section of Your account opens with one sentence that says what it holds. Where a choice needs explaining (who sees a field, the second factor, passkeys, tokens, sessions), a link to the matching page of the user guide at the documentation address of NAV-068 follows the explanation, its leave mark also given in words to screen readers; the password part has none (an instance without a documentation address needs its own study).
- **ACC-108** · new · Security holds, in this order, the password, two-step verification, passkeys, personal API tokens and recent devices, each with a bold heading and an explanation. The last two end with a link on its own line to a screen of its own, Tokens (ACC-079) and Sessions (ACC-074), which keep Security as the selected tab (the way back from them needs its own study).
- **ACC-109** · new · Privacy holds Download my data (ACC-027). Preferences ends with removing the account: because every account asks an administrator for removal (ACC-027), a notice says so for every account, beside the button that asks.
- **ACC-110** · new · Your account never offers a control that cannot work for this account (NAV-004). Where the identity provider or an administrator handles something, a notice takes the control's place and says who handles it and where: the password and the second factor of an account of the provider, its passkeys while ACC-100 holds, its e-mail address, the fields the provider fills and locks, and removing the account.
- **ACC-111** · new · When fields are locked, Profile says so once in a notice at its top, and each locked field still shows its lock. On Security the notice that replaces the password form sits directly under the part's heading with no sentence before it, and a notice has a bold title, one or two lines and, where it helps, a link to the user guide last.
- **ACC-112** · new · The **E-mail** section shows, under a bold sub-heading, a sentence that holds the account's address in bold, then a read-only line with a small icon that says how the person signs in: password, authenticator, passkeys, or the identity provider, with no control beside it.
- **ACC-113** · new · For an account of the identity provider, a notice under the address says it is changed at the provider; a local account gets the change of ACC-086 there. A second sub-heading with one sentence points to the notification preferences for mail from Diffluence, and nothing points to marketing mail, which Diffluence never sends (SEC-900).
- **ACC-114** · new · A person edits their own profile in place, in Your account, Profile and visibility: the fields come in groups, picture and header, about you, and contact, each a slightly rounded card a shade off the page under a heading that stands above it, with no lines between rows (changes the design standard, decided 2026-11-14).
- **ACC-115** · new · Each profile row shows a small bold label with the value under it, or a dim placeholder that invites the person to add it, at the start, and its visibility chooser at the end: borderless, with an icon for the audience, its name and an arrow. The choosers line up in one column down the card, under one small muted caption per card.
- **ACC-116** · new · A profile field looks like text at rest, becomes an input when selected, and saves when it is left, which a live region announces (NAV-080); Escape undoes the change. This replaces the Edit button of spec 013 F4 on a person's own profile.
- **ACC-117** · new · The about-you card lists, in this order, the name, pronouns, job title, department, organisation, location, local time and short text, and the contact card holds the e-mail address. The name has no visibility chooser, because names on a person's work always show (PRM-083), so no second, public name is offered.
- **ACC-118** · new · Beyond ACC-020, a profile also holds the person's pronouns and the organisation they work for, both optional short plain text, each with its own visibility. An identity provider can fill and lock the organisation as it does title and department (ACC-023), and the organisation helps others tell where a guest comes from.
- **ACC-119** · new · The profile picture has its own visibility, like the other fields: everyone who may see the profile, members only, or only me, and a viewer who may not see it gets the initials. The question who may see the picture and its chooser stand stacked at the end of the picture card, under the header, and no choice reaches people without an account (deliberate difference 1).
- **ACC-120** · new · On a person's own profile, a missing time zone shows in the local time row as not set, with a link to Preferences where it is chosen, and the time zone chooser there shows a placeholder while it is empty. Other viewers still see no local time (spec 013 F4).
- **ACC-121** · later · A person can add a header image across the top of their profile, uploaded and checked like any image (ADM-013), never fetched from an outside library (deliberate difference 5). Without one the header is a soft tint chosen from the name, as the initials are (ACC-022), and the round picture sits half over its lower start corner, set off by a ring.
- **ACC-122** · later · Your account lists the apps a person has allowed to act in their name, with what each may do and when it last did something, and the person can withdraw that permission from each app. It comes with OAuth for the API in phase 7 (ADR-026, SEC-234, PLT-039).

- **ACC-129** · later · A team has a name, a square tile in a colour name of its own with a people mark, its members and the people who run it. - **ACC-130** · later · The administration lists all teams: Create team as the one primary action and team settings as a normal button at the end of the title row, two tiles of half width that count all teams and the teams an administrator runs, a search by team name, a count line, and a table with the columns team (its tile and name), run by, and members, with no row menu.
- **ACC-131** · later · With teams, the Groups table gains a team column between used in and source, which names the team a group belongs to or says none.
- **ACC-132** · later · An administrator decides which teams may be given access to spaces and pages: all teams, only teams an administrator runs, or none; with none, access goes only to people, groups and the classes all members and all guests. - **ACC-137** · later · The sign-in rules for guests are login policies whose people are guests (ACC-090), listed in a table with the columns policy (its name as a link), people, second factor and API tokens. The one primary action makes a new policy for guests, and a normal button after it makes a trial policy for a few guests (ACC-095, NAV-164).
- **ACC-138** · later · A guest signs in as a member does, with a password and the second factor of their policy, a passkey, or through the identity provider, and never with only a code sent by e-mail (ASVS 6.3.6, ACC-002). - **ACC-139** · new · Beyond ACC-041, the Users screen of the administration has a normal button between Invite and More (ADM-080) that opens the invitation requests waiting for approval in the Invitations section (ADM-070), with the number waiting inside it, also in words for screen readers (how it shows while nothing waits needs its own study).
- **ACC-140** · new · Beyond ACC-043, service accounts have a section of their own in the administration, beside users and groups (ADM-070), which lists each with its name, the person responsible, its tokens with their end dates and last use, and the rules that act as it (PLT-023). - **ACC-141** · new · While there is no service account, that section's title row has no button, and one centred block holds a short heading, one or two sentences saying that a service account keeps automation working when people change teams or leave, Create service account as the one primary action, and a link to the user guide right under it.

## 9.6 The permission model

- **ACC-049** · built · Three layers: global permissions, space permissions and page restrictions.
- **ACC-050** · built · **The rule:** a person may do something on a page when they may use the product, and their space permission allows it, and no view restriction above or on the page excludes them, and for edits no edit restriction on the page excludes them.
- **ACC-051** · built · Permissions only allow. There is no explicit deny.
- **ACC-052** · built · No grant means no access, also for administrators.
- **ACC-053** · built · A view restriction applies to the page and everything below it. An edit restriction applies to that page only.
- **ACC-054** · built · Restrictions can only narrow. A person on a restriction list with no space access gets nothing.
- **ACC-055** · built · The same rule is used in one function, and in the SQL for lists. Thousands of generated cases compare them.
- **ACC-056** · built · A person who may not view gets "not found". A person who may view but not act gets "forbidden".
- **ACC-057** · built · Every refusal is audited as denied.
- **ACC-058** · built · Global permissions are: use the product, create spaces, view profiles, administrator, system administrator.
- **ACC-059** · built · A global permission **create personal space**.
- **ACC-060** · built · Global permission screens show who has each permission through which group.
- **ACC-148** · new · Beyond ACC-060, the instance permissions screen is a table with one row per group and one column per instance permission: use the product, create spaces, create personal space, view profiles, invite people, administrator and system administrator. Each cell shows granted or not granted by a tick or a cross in a round mark, also in words for screen readers, and the rows come in name order with no sort, paging, totals or bulk actions.
- **ACC-149** · new · The table's first heading counts the groups; above it a field narrows the rows by group name, a Filters button narrows them further, and Edit stands alone at the end of that row. A group that holds administrator carries an outlined tag after its name, and a row with more to show opens from an arrow at its start, which is left out where there is nothing to open (what the filters offer and what an opened row shows need their own study).
- **ACC-150** · new · Manage groups, a normal button at the end of the title row, leads to the groups section. The table is read-only until Edit; then a changed row gets its new set as an instance role, the built-in one where it matches (PRM-189), a preview shows who gains and loses what before saving (SPC-057), granting administrator asks for the password again (SEC-605), and only a system administrator changes the system administrator column (PRM-008).
- **ACC-151** · new · People who hold an instance permission directly, not through a group, appear on the instance permissions screen too (whether as rows after the groups or on a second tab needs its own study).
- **ACC-152** · new · Beyond PRM-191, the roles screen has a title without description and three sections in this order, each with a heading and one line of text that holds a link to the user guide: built-in space roles, custom space roles, and instance roles (spec 036). It has no search, sort, filter or heading row (changes the design standard, decided 2026-11-14).
- **ACC-153** · new · Built-in space roles come first, in a card of rows with full-width dividers, from the most to the least powerful: Space admin, Manager, Editor, Viewer (PRM-179). Each row shows the name as plain text, one muted line on what the role is for, a tag with the number of permissions it holds, how many hold it, and an icon-only row menu at the end; a built-in role cannot be changed (what the row menus offer needs its own study).
- **ACC-154** · new · Custom space roles follow: a line with Add, the one primary action, at its end and the counter of ACC-155 at its start, then a card holding the list, or one muted sentence that none exists yet. Instance roles follow in the same form.
- **ACC-155** · later · The instance has a limit on the number of custom space roles, and the roles screen says how many more can still be made. Roles that PRM-189 and PRM-218 make by themselves never count towards it, so the limit never refuses such a conversion (the number, and a limit for instance roles, need their own study).
- **ACC-156** · new · An administrator exports the permissions of the whole instance as a CSV file, in one of two forms chosen on a screen of its own: every space role in use, including combinations without a name (PRM-218), with its permissions and how many people and groups hold it, to help decide which roles to make; or every grant, to audit who reaches which spaces. The first form is chosen at the start, and one must always be chosen.
- **ACC-157** · new · The grant form lists each instance permission and each role in each space with the person or group that holds it, and for a person whether directly or through which group; pages with restrictions of their own are listed by space key and page id, never by title (ADR-029). Neither form holds content (deliberate difference 2), and the columns need their own study.
- **ACC-158** · new · The permissions export starts from one primary button, runs in the background and ends with a notification and a link valid for 24 hours for its maker only (EXC-014, PRM-094); there is no choice of format, spaces or people, no list of earlier exports, and no progress or cancel. Only administrators make it, and every export is audited.
- **ACC-159** · new · The two forms are two options in one lightly raised card, each with a bold name, a description and a line that starts with a bold lead-in saying what the form is best for, the texts lined up with the name rather than the option's circle and an inset line between the options. Under the start button a note says, in words as well as by a mark, that a choice is required (changes the design standard, decided 2026-11-14).
- **ACC-160** · new · An administrator sees one overview of access across all spaces: for each space, the people, groups and classes that hold each role there, filtered by space, person, group and role, paged on large instances, and downloadable as CSV. It names spaces, people and roles, never page titles or content (deliberate difference 2), and its layout and load budget need their own study.
- **ACC-161** · later · An administrator can replace one space role by another for everyone who holds it, in every space at once, for example a combination without a name by a named role. A preview first says how many people, groups and spaces change and what they gain and lose (PRM-183), and the change is audited per space.
- **ACC-162** · later · A replacement that keeps or narrows access runs for an administrator, while one that widens access in a space shows per space in the preview and tells that space's administrators, because space roles are given in the space (PRM-186). It never gives Space admin (PRM-184), never leaves a space without an administrator (PRM-185), runs in the background with a report (SPC-064), and the emptied role can then be deleted (PRM-182).

## 9.7 Page restrictions

- **ACC-061** · built · The lock opens the restrictions of the page: who can view it and everything below it, and who can edit it.
- **ACC-062** · built · The dialog shows restrictions inherited from pages above.
- **ACC-063** · built · Restrictions are managed by people with *manage restrictions*, who can see the page.
- **ACC-064** · built · Three clear states at the top of the dialog: **Open** (everyone in the space can view and edit), **View only for most** (everyone can view, chosen people can edit), and **Private** (only chosen people).
- **ACC-065** · built · A person setting a restriction is added to it, so nobody locks themselves out by accident.
- **ACC-066** · built · The lock icon shows the state: open when the page has no restrictions of its own, closed when it has. Everyone who can see the page can see that it is restricted. See spec 030.
- **ACC-067** · built · A list in space settings shows all restricted pages (SPC-065). It is the flag `restricted` on the Content screen of a space (SPC-065).
- **ACC-068** · built · The dialog says how many pages below are affected.
- **ACC-163** · new · Beyond ACC-067, Space settings holds a report of restrictions among its content settings, with one sentence saying that it lists pages and live documents limited to chosen people or groups. Its table has the columns item (a type icon, the title as a link and the space muted after it), kind, person or group, added by (a link to that person), added on (a date) and an action, and the kind, view or edit, is the only bold text in a row.
- **ACC-164** · new · The report has one row per item, kind and person or group, and the rows of one item form a group whose title shows in its first row only. It has no filters, search, paging or export, and lists only items the person may see, leaving out the rest without a count; recovering access (ACC-070) is the way to them.
- **ACC-165** · new · A person with *manage restrictions* removes one entry from its row with an icon-only action centred in the last column, which first shows who gains what, as a move does (PAG-044), and never removes the person's own last way to view (ACC-065). A view entry shows an information mark in that place (whether view entries can be removed here too, and whether who added an entry and when comes from the audit log, need their own study).

## 9.8 When something is off

- **ACC-069** · built · **Why can or can't I?** Space administrators and administrators ask, for any person and action on a page, for the result and the layer that decided it. It uses the same evaluation as the real check.
- **ACC-070** · built · **Recover access:** an administrator gives themselves access to a space or page, with a reason. It is always audited.
- **ACC-071** · built · The author of a page is notified when an administrator recovers access to it.
- **ACC-072** · new · Share has an **inspect** entry that opens the same explanation for a person who asked for access.
- **ACC-073** · partly · When the last person on a restriction is disabled, a space administrator is told, and can recover the page. Built: the console lists such a page without its title, and an administrator can recover it. Still open: a notification to the space administrator, because a notification about a page they cannot see does not show.
- **ACC-166** · new · The administration has an **access check**: an administrator picks one person or one group, sees who it is, and downloads a CSV of every space that person or group can reach, with the role held there and the route, directly or through which group. It uses the same rule as the real check (ACC-055), names spaces and roles only (deliberate difference 2), and each download is audited.
- **ACC-167** · new · A second part of the access check takes one page and one action for the chosen person or group, and shows the result and the layer that decided it, as ACC-069 does from a page; a page the administrator cannot see is named by its id (ADR-029).
- **ACC-168** · new · The access check shows its title with one line on what it does, the picker with its label, a line, and then an identity block: a large round picture with the name beside it in bold and larger and the e-mail address muted under the name, or for a group its mark, name and number of members. Its two parts follow, each with a bold sub-heading, a hint and its action; the download is a normal button, and the screen has no primary button.

## 9.9 Where people may connect from

Rules on network addresses decide from where the instance, or only its administration, can be reached.

- **ACC-169** · later · An administrator can limit the whole instance, or only the administration, to listed network addresses and ranges. A rule has a name, a state (on, off, or trying, when a request from elsewhere is only recorded) and what it limits, and the list shows these three columns, or one sentence when no rule exists.
- **ACC-170** · later · A request from outside an active rule gets a plain refusal that tells nothing more, and every refusal is audited. The real address comes only through trusted proxies (SEC-012), and there are no conditions on devices, because the instance knows no devices (SEC-181).
- **ACC-171** · later · The command line on the host always works, so a wrong rule never locks the last administrator out for good (PRM-007, SEC-609), and a change to a rule asks for the password again and is audited (tokens, SCIM and incoming hooks, ranges in IPv6, and how trying shows what it recorded need their own study).
