# 09.4: What readers see, and keeping drafts out of sight

How to read this chapter: see [01-document-control.md](01-document-control.md).

The core promise of document control is simple: people who rely on a document only ever see the approved version, and an unapproved change never reaches them by accident. ISO 9001 7.5.3.1 asks that documented information is available and suitable for use where and when needed, and adequately protected; 7.5.3.2 asks for control of distribution and access, and for prevention of the unintended use of obsolete information. Every line in this chapter serves that promise, and the rule is decided in one place so that no screen can break it.

## 4.1 Who sees which version

- **DOC-300** · new · For a controlled page, the permission rule answers one question for a person: may they see the **working version**? The answer is yes for authors (`page.edit` on the page) and for reviewers of the open round (DOC-203); for everyone else it is no, and they see the **approved version**. *Why:* one rule in one place, so that pages, the tree, search, exports, the feed, notifications, the API and the public site cannot disagree (Part 11 §11.10(d), limiting access to authorised people). *Edge cases:* a person with `page.edit` through a group sees the working version; losing that right while a page is open makes the next request show the approved version. *Proof:* a permission matrix of reader, author, reviewer, former reviewer, administrator and guest across every state kind, on every read route; the "never show what one may not see" test pattern of waves R and PF.
- **DOC-301** · new · A controlled page that was **never approved** does not exist for a reader: it is absent from the tree, search, the feed, links, the space's content screen and the API, exactly as a page they may not view (decided, DOC-1406). *Why:* readers can only rely on approved content; a half-written procedure is not a document yet. *Edge cases:* its child pages that are approved are shown under the nearest visible parent, like pages under a restricted parent today. *Proof:* tests on every route; a mutation that shows an unapproved page must be caught.
- **DOC-302** · new · A reader sees, near the title, the state (by its name), the version number, when it was approved, and by whom, with a link to the approval record when they may see it. *Why:* ISO 9001 7.5.2 a asks for identification of documented information, including a version. *Proof:* an e2e picture of the reader band.
- **DOC-303** · new · An author or reviewer sees the working version with a clear band "not approved yet", the state it is in, and a switch "show the approved version". The band never disappears while the working version differs from the approved one. *Why:* people who see both must never mistake one for the other. *Edge cases:* when there is no approved version yet, the switch is absent and the band says "never approved". *Proof:* e2e pictures and an accessibility check of the band.

## 4.2 What starts a new review

- **DOC-310** · new · **Any published change** to approved content (title, body, attachments that are shown, page properties used in conditions) creates a working version and moves the page to the start state, or to the state the workflow names for a change. The approved version stays what readers see. *Why:* ISO 9001 7.5.2 c: changes are reviewed and approved like the original. *Edge cases:* changes that are not content do not restart review: labels, the page owner, watchers, moves within the space (09.13 covers moves between spaces), and comments. Saving a draft without publishing never restarts anything. *Proof:* a table test of which changes restart and which do not; a mutation that skips the restart must be caught.
- **DOC-311** · new · A **silent** publish (no notification) is still a change and still restarts review; "silent" only affects notifications. *Why:* otherwise "silent" would become a way around control. *Proof:* a test.
- **DOC-312** · new · Restoring an older version (version history, "restore this version") creates a new working version with that content, which then goes through review like any change. It never makes an old version current for readers without review. *Why:* restore is a change. *Edge cases:* restoring the current approved version onto a working version that differs creates a working version equal to the approved one; when the working version and the approved version are equal again, the page returns to its approved state without review (decided, DOC-1410), because nothing differs from what was approved. *Proof:* tests for both cases.

## 4.3 Obsolete versions

- **DOC-320** · new · When a new version is approved, the previous approved version becomes **obsolete**. It stays readable in the history to those who may see history, marked "obsolete since" with a link to the current one, and it never appears as the current text anywhere. *Why:* ISO 9001 7.5.3.2 d and the clause on retention: obsolete information is kept from unintended use but retained. *Proof:* tests that the history shows the mark and that no read route returns the obsolete text as current.
- **DOC-321** · new · A link to a specific version (`?version=N`) shows that version only to people who may see history; to a reader it answers as if the page had no such version. *Why:* links in mails and chats must not leak working or obsolete text. *Proof:* tests for each kind of person.
- **DOC-322** · new · A **withdrawn** document (moved to an *obsolete* state by a transition, not replaced) disappears from readers like an archived page and shows a banner "withdrawn on" to those who may still see it. *Why:* organisations withdraw procedures that no longer apply, without deleting the record (ISO 9001 7.5.3.2 d). *Proof:* tests on every read route.

## 4.4 Edits while a round runs

- **DOC-330** · new · Publishing a new change while a round is open **ends the round** as "superseded" and starts a new one on the new working version. Answers given to the old version stay on record but do not count for the new one. *Why:* a reviewer approved a specific text (Part 11 §11.70 binds a signature to its record); approval of an earlier text does not cover a later one. Today's rounds already end on publish (`endRoundsOnPublish`). *Proof:* a test that an approval of the superseded text is not counted.
- **DOC-331** · new · A workflow state can **lock editing** while a round runs, so that authors cannot publish until the round ends (decided: off by default, DOC-1411). *Why:* some teams want a stable text during review. *Proof:* a test that publish is refused with the reason while locked.
- **DOC-332** · new · Editing together (the collab service) continues on the working version during review, and readers never receive the live document stream of a controlled page; they get the approved version only. *Why:* the live stream would leak the working text. *Edge cases:* a reader who holds an open editor session when a page becomes controlled is disconnected from the stream at once. *Proof:* a test that a reader's collab connection is refused for a controlled page; a test of the disconnect.
