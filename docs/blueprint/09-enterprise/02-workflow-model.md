# 09.2: The workflow model, states and transitions

How to read this chapter: see [01-document-control.md](01-document-control.md). Every line has a number, a status (**built**, **partly**, **new**, **later**), the behaviour, the reason, the edge cases and the proof. "New" lines are planned in [spec 064](../../specs/064-document-control.md). Reasons cite a clause of a standard where one applies; the standards are listed in [sources.md](sources.md).

A workflow is the agreed path a controlled document takes from being written to being relied on. ISO 9001 clause 7.5.2 asks that documented information is reviewed and approved for suitability and adequacy before use; clause 7.5.3 asks that it is controlled so the right version is available where needed and protected from unintended change. A workflow is how Diffluence makes that path explicit, repeatable and recorded.

## 2.1 What a workflow is

- **DOC-100** · new · A **workflow** belongs to one space and has a name, a description, a list of states, a list of transitions, and the kinds of item it governs (page, blog post, database; never folders or links). *Why:* ISO 9001 7.5.2 requires a defined review and approval before use; a named, described workflow is the defined procedure an auditor asks to see. *Edge cases:* two workflows in one space may share a name only if one is archived; the name must be unique among active workflows of the space, because people pick it from a list. A workflow that governs no kind of item is refused when saved. *Proof:* unit tests of the validator for a missing name, a duplicate active name and an empty kind list; an API test that a refused workflow is not stored.
- **DOC-101** · new · A **state** has a stable identifier, a display name in the space's language, an optional description, and a **kind**: *draft*, *in review*, *approved*, *rejected* or *obsolete*. The kind, not the name, is what the rest of Diffluence understands: readers, search, exports, sites and notifications all decide by kind. *Why:* names differ by organisation and language ("Freigegeben", "Released", "Effective"), while the meaning must stay machine-checkable for the visibility rule. *Edge cases:* renaming a state never changes its identifier, so history and audit keep pointing to the right state; two states may share a kind (for example two review stages), but they must have different names. *Proof:* tests that renaming a state keeps the round history linked; a matrix test that visibility depends on kind only.
- **DOC-102** · new · Exactly one state is the **start**, and it must be of kind *draft*. At least one state is of kind *approved*. Every state must be reachable from the start, and from every state of kind *draft*, *in review* or *rejected* there must be a path to an approved state. A workflow that breaks one of these rules is refused when saved, and the message names the rule and the state. *Why:* a workflow that can never reach approval would hold readers on an old version for ever (ISO 9001 7.5.3.1 a: available where needed). *Edge cases:* a state of kind *obsolete* may be a dead end, because that is its meaning; a cycle back to draft is allowed. *Proof:* a graph validator with table tests for each rule, plus a fuzz test over random graphs that the validator never accepts a graph without a path to approved.
- **DOC-103** · new · A state of kind *approved* may be **final** (a document stays approved until changed) or **timed**, in which case periodic review applies (09.9). *Why:* EU GMP Annex 11 clause 11 asks for periodic evaluation; not every document needs it, so it is a property of the state. *Edge cases:* a workflow can have two approved states, for example "approved for training" and "effective"; readers see the newest version in any approved state. *Proof:* tests with two approved states that readers get the latest approved version regardless of which approved state it is in.
- **DOC-104** · new · A **transition** goes from one state to one other state and has a name shown on its button, an optional description, who may take it (09.3), and what it requires: a comment, a due date for the next state, a signature with a meaning (09.8), or that the round is passed (all, quorum or any, 09.3). *Why:* Part 11 §11.10(e) asks that the audit trail records the operator's actions; a transition is one such action, so it must be an explicit, named step. *Edge cases:* a transition from a state to itself is refused, because it would record a step without a change; two transitions between the same pair of states are allowed if their names differ (for example "approve" and "approve with signature"). *Proof:* validator tests; an audit test that each transition writes one entry with the from-state, to-state, transition name and person.
- **DOC-105** · new · Some transitions are taken by the **system**: when a round passes, when a due date passes (09.3), or when a published change arrives on approved content (09.4). A system transition records "system" and the cause in the audit entry, never a person. *Why:* Part 11 §11.10(e) requires that the audit trail is computer-generated and does not attribute actions to someone who did not take them. *Edge cases:* a system transition into a state of kind *approved* is only allowed as the result of a passed round, never on a time-out (decided, DOC-1401). *Proof:* tests that a due-date job never moves a page into an approved state; a mutation that allows it must be caught.

## 2.2 Versions of a workflow

- **DOC-110** · new · A workflow is **versioned**. Saving a change makes a new version, and the old version stays readable. Each round of review is bound to the workflow version it started under, and keeps it until the round ends, even if the workflow changes meanwhile. *Why:* ISO 9001 7.5.3.2 asks for control of changes; a running review must not change its rules halfway. *Edge cases:* removing a state that a page currently sits in is refused, with a list of the pages; the administrator first moves those pages or ends their rounds. Renaming a state is allowed while pages sit in it. *Proof:* a test that a round started under version 1 keeps its reviewers and rule after version 2 changes them; a test that removing an occupied state is refused.
- **DOC-111** · new · A new page entering a workflow, or an approved page that starts a new round, uses the **newest** workflow version. *Why:* the change control of the workflow itself must take effect for new work. *Edge cases:* a page in a draft state with no open round moves to the newest version at its next transition. *Proof:* a test across two workflow versions.
- **DOC-112** · new · The history of a workflow shows each version, who saved it, when, and a readable list of what changed (states added, removed or renamed, transitions changed, reviewers changed). It is visible to those with `space.workflows` or `space.audit`. *Why:* auditors ask how the procedure itself was controlled. *Proof:* an API test of the change list for each kind of change.

## 2.3 Conditions

- **DOC-120** · new · A transition may have **conditions** that must hold before it can be taken: a label is present or absent; a page property has a given value; the change since the last approved version touches the title, the body or the attachments; or the page has at least one attachment. When a condition fails, the button is disabled and says why. *Why:* teams often need simple gates, such as "only pages labelled SOP need the signature step", without scripting. *Edge cases:* a condition on a label that was renamed keeps working, because it refers to the label's identifier; a condition on a property that was removed from the space fails closed, with the reason "the property no longer exists". *Proof:* table tests per condition kind; a test of the fail-closed case.
- **DOC-121** · new · There is **no scripting** in conditions or transitions (decided, DOC-1404). Automation flows (blueprint 08, later) may take a transition on behalf of their owner, through the same checks as a person, but never sign. *Why:* a script is hard to review and audit; regulated teams must be able to read the rule. *Proof:* a test that an automation run without the right to take a transition is refused.
- **DOC-122** · later · Conditions on the result of a check outside Diffluence (for example a ticket being closed in a linked tool, roadmap item "connectors"). *Why:* useful, but it depends on connectors that do not exist yet.

## 2.4 Instance templates

- **DOC-130** · new · An instance administrator can publish a workflow as an **instance template**. A space administrator with `space.workflows` can copy a template into the space, and then change the copy. The copy records which template and version it came from. *Why:* organisations want the same procedure everywhere, but each space must be able to adjust and own it. *Edge cases:* changing the template later does not change the copies (decided, DOC-1405); the template screen shows which spaces use an older version, and a space administrator can compare and take the new version by choice. *Proof:* a test that a template change leaves copies untouched; a test of the comparison.
- **DOC-131** · new · Diffluence ships two example templates, so a space can start at once: "review then approve" (draft, in review, approved, rejected back to draft) and "two-step with signature" (draft, technical review, quality approval with a signature of meaning "approved", effective). Their names and texts are written for Diffluence and are translated. *Why:* an empty editor is a hard start; examples teach the model. *Proof:* a test that both examples pass the validator of DOC-102.

## 2.5 Turning workflows on and off

- **DOC-140** · new · Assigning a workflow to a space or a page is a step with a preview: how many pages are affected, in which state each lands (pages approved today land in the first approved state, others in the start state), and what readers will see afterwards. The step is applied only after confirmation, in one transaction, and audited. *Why:* turning on control can hide pages from readers (09.4); the person must see that before it happens. *Edge cases:* a space with thousands of pages runs the assignment as background work with progress, and readers see the old state until it is done for their page. *Proof:* a test of the preview numbers; a test that a failed assignment leaves no page half-assigned.
- **DOC-141** · new · Removing a workflow from a space or a page keeps every round, answer and signature on record. The page becomes an ordinary page. Readers keep seeing the last approved version until the next publish, so turning control off never shows an unapproved text by surprise (decided, DOC-1407). *Proof:* a test that a working version stays hidden after removal until the next publish.
