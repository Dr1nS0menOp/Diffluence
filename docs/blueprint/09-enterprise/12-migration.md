# 09.12: Migration of today's approvals

How to read this chapter: see [01-document-control.md](01-document-control.md).

Teams already use today's approvals: rounds with chosen approvers, a space rule that requires approval before publishing, and up to ten fixed approvers per space (PAG-062 to PAG-069). Document control must not break them, must not change what readers see without a person's choice, and must keep every past record. The upgrade machinery (expand and contract migrations, the one-day grace of wave O2, the backup rule of wave FU) applies as always.

- **DOC-1100** · new · The migration that adds document control is **expand only**: new tables, no change to `approval_rounds`, `approval_answers`, `spaces.approval_required` or `space_approvers`. Today's approvals keep working unchanged until an administrator moves a space to a workflow. *Why:* the upgrade promise of blueprint 07: a release must run beside the previous one on the same database. *Proof:* the upgrade test across the release; a test that today's approval flow still passes after the migration.
- **DOC-1101** · new · For each space that **requires approval** today, Space settings offers, not forces, a **generated workflow** that means the same: a start state "Draft", a review state with the space's fixed approvers and the rule "all", and an approved state, with independence off (because today's rule does not ask for it). The offer shows exactly what changes for readers (09.4) before it is accepted (decided, DOC-1420). *Why:* no behaviour changes without an administrator's choice. *Proof:* a test that the generated workflow, applied, gives the same approval outcome as today's rule for the same answers.
- **DOC-1102** · new · Accepting the offer assigns the workflow (DOC-140). A page whose latest version was approved by a round today lands in the approved state at that version. A page with an older approved version lands with that version as approved and its newer published version as a working version, so readers see the approved one. A page never approved lands in the start state and is hidden from readers (DOC-301); the preview counts these pages separately and warns in plain words. *Why:* this is the moment readers' view changes, so it must be visible and counted. *Proof:* a test for each of the three cases.
- **DOC-1103** · new · Approvals carried over from today's rounds are marked "approved before signatures" and link to the old round. They count as approvals, not as signatures. *Why:* Part 11 §11.70 and §11.50: they were not signed, and must not appear to be. *Proof:* a test that no signature record is created for carried-over approvals.
- **DOC-1104** · new · Spaces that do **not** require approval today, but use ad-hoc rounds on some pages, keep those rounds as they are; nothing is offered. *Proof:* a test.
- **DOC-1105** · new · After a space moves to a workflow, the old approval rule of that space is switched off and hidden, and its fixed approvers stay readable as history. The old "ask for approval" action on its pages becomes "start a review" under the workflow. *Proof:* a test.
- **DOC-1106** · new · A later release may **contract**: remove the old approval rule from spaces that moved, after the grace and with the checks of wave O2. Only spaces that did not move keep the old tables in use. Today's rounds stay readable for ever as records. *Proof:* covered by the contract migration test when it is written.
- **DOC-1107** · new · The migration of a space is reversible until the first round runs under the workflow: an administrator can undo it, and today's rule returns. After that, removing the workflow follows DOC-141. *Why:* a safe trial. *Proof:* a test of undo before and refusal after the first round.
