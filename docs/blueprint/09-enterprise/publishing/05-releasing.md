# 09.P5: Releasing one page, a branch or the whole space

How to read this chapter: see [01-draft-and-published-spaces.md](01-draft-and-published-spaces.md).

A release copies what is out of step from the draft space into the published space. It can take one page, a page and everything below it, or the whole space. Every release is a **run**: it has a preview, a person or an approval that started it, a list of pages with the versions it takes, and an outcome. This chapter says what each scope does, how leaving out and taking off work, and how a run behaves.

## 5.1 Scopes

- **PUB-400** · built · **One page.** From the draft page's More menu, or from the release screen, a person with `space.release` releases that page: its current version (or for a controlled page its approved version, PUB-700), its title, place, look, labels and files. *Why:* corrections should reach readers without waiting for the whole space. *Edge cases:* if the page's parent has no twin, the page goes under its nearest released ancestor, or at the top of the published space, and the run's report says so (decided, PUB-1426); a page left out cannot be released alone until it is included again. *Proof:* tests of a first release, a second release, and a page whose parent is not released.
- **PUB-401** · new · **A branch.** The same, for a page and every page below it that is out of step and not left out. *Why:* a chapter of a guide changes together. *Edge cases:* a page below that is left out is skipped with its own pages below it, because releasing a child of a page readers do not have would put it in a place readers do not expect; the preview lists them. *Proof:* tests with a left-out page inside the branch.
- **PUB-402** · new · **The whole space.** Every page that is out of step or not released yet, except those left out; and, by default, taking off the pages removed or archived in the draft (decided, PUB-1410). *Why:* a product release, a new edition of a policy set. *Proof:* tests of a first whole-space release and of a later one that sends only what changed.
- **PUB-403** · built · A release never takes a page that is **in step**, so releasing the whole space twice in a row makes no versions the second time. *Why:* readers' histories and watchers' mail must not fill with empty versions. *Proof:* a test.

## 5.2 What a release writes

- **PUB-410** · built · For each page in a run: the twin is made if it has none (as an ordinary page of the published space, created by the releaser), and gets **one new version** with the title and the document with links rewritten (06), comment anchors and instruction text removed (PUB-511), and files mapped to their copies (PUB-320). Its look and labels are set to the draft's. The version's summary is the run's release note; it is silent when the run is silent (PUB-821). *Why:* one version per release keeps the published history readable (PUB-332). *Proof:* a test that compares a released page with its draft field by field.
- **PUB-411** · built · A page whose only out-of-step aspect is its place, look or labels gets **no new version**: the twin is moved or changed, and the change is audited. *Why:* a version means the text changed, as it does elsewhere in Diffluence. *Proof:* a test that a moved page's history in the published space is unchanged.
- **PUB-412** · new · Within a run, pages are written **parents before children**, and the children of each released parent are ordered in the published space as in the draft, with siblings that are not released kept after them in their own order. *Why:* readers see the order the writers chose. *Proof:* a test with siblings released and not released.
- **PUB-413** · built · The releaser needs, at the moment of the run: `space.release` in the draft space, view of each page released (as for a copy), and `space.view` in the published space (decided, PUB-1420). The release then writes the published space as the release path, not through the releaser's rights in that space, which are only view. *Why:* the published space is managed (PUB-220); rights there are about reading. *Edge cases:* a page the releaser may not view in the draft (restricted from them) is not in their run and the preview says how many such pages were skipped, without their titles. *Proof:* matrix tests for each right missing.

## 5.3 Leaving pages out

- **PUB-420** · new · A person with `space.release` can mark a draft page **left out**, alone or with everything below it. Left-out pages are never in a branch or whole-space run, and a single-page release of one is refused with the reason. Leaving out is audited, with an optional reason shown on the release screen. *Why:* working notes, internal sections and pages not ready yet live beside the text that readers get. *Edge cases:* new pages created below a page left out "with everything below it" are left out too; a page moved out of such a branch is included again, and the move dialog says so. *Proof:* tests for one page, a branch, a new child and a move out.
- **PUB-421** · new · Leaving out a page that is **already released** asks one question: take it off the published space now, or keep the last released version there as it is. Kept, its twin no longer changes and its status is **Left out (still published)**. *Why:* both are common: a page retired from the guide, and a page frozen while it is rewritten. *Proof:* tests of both answers.
- **PUB-422** · new · A draft page with a **view restriction** is left out of branch and whole-space runs unless it was released by itself before, or the person names it in the preview (decided, PUB-1405). The preview shows how many restricted pages were left out this way, and lists those the person may see. *Why:* a restriction in the draft space usually means "not for everyone"; a bulk act must not undo that. *Proof:* tests that a restricted page stays out of a whole-space run, and goes in when named.
- **PUB-423** · new · Including a page again removes the mark and makes the page **Not released yet** or **Changed since release**, as it is. *Proof:* a test.

## 5.4 Taking pages off

- **PUB-440** · new · A person with `space.release` can **take off** a released page, alone or with everything below it: the twins go to the published space's trash, where the published space's administrators can see them for the trash retention, and the page pairs end. Taking off is a run of its own, with a preview and a note, and is audited. *Why:* a page that is wrong or no longer valid must leave readers at once, without deleting the draft. *Edge cases:* a twin's released children that are not taken off move to the twin's nearest remaining ancestor and the preview lists them; the published space's home page cannot be taken off. *Proof:* tests of one page, a branch, and a branch with children kept.
- **PUB-441** · new · Taking off never **purges**: the twin can only be purged by the published space's trash retention or by a purge from its trash by an administrator of the published space. *Why:* a mistaken take-off must be undoable (PUB-1422). *Proof:* a test.
- **PUB-442** · new · Releasing a page again after it was taken off makes a **new twin** (PUB-201); a twin still in the published space's trash stays there. *Why:* restoring the old twin would bring back its old reader comments on a page that was gone; a new twin is clear. *Proof:* a test.

## 5.5 The preview and the run

- **PUB-430** · partly · Every release starts with a **preview**: the pages that will be made, changed (with their aspects), moved, taken off and left out, each as a count and as a list; the files that will be copied with their total size against the published space's room; pages that cannot be released with the reason; pages placed higher than in the draft (PUB-1426); and links that will stay text because their target is not released (PUB-512). The person adds a release note, chooses silent or not, and confirms. *Why:* the preview is where a release manager catches the page that should not go; enterprise CMS tools that publish references show the same need (02). *Proof:* tests of each count against a seeded space.
- **PUB-431** · built · The run releases exactly the **versions shown in the preview** (decided, PUB-1409). A page that changed after the preview is released at the previewed version and stays Changed since release. A page that was deleted, moved out of the space or left out after the preview is skipped and the report says so. *Why:* the person approved what they saw; versions are immutable, so this is exact. *Proof:* tests for each change between preview and run.
- **PUB-432** · new · From the preview and the release screen, each changed page opens a **compare** of its released version with the version to be released (PUB-344). *Why:* the reviewer must see what readers will get, as docs-as-code previews show (02). *Proof:* an e2e test.
- **PUB-433** · built · A preview is valid for **one hour**; confirming an older preview asks to make a new one. *Why:* a preview left open overnight no longer says what will happen. *Proof:* a test with a fixed clock.
- **PUB-450** · built · A run of up to **1,000** pages is applied in **one transaction**: readers see the published space as it was or as it will be, never half (decided, PUB-1411). *Why:* a guide changes together (02, reason 2). *Proof:* a test that reads from another connection during the run and sees no released page before the commit.
- **PUB-451** · new · A larger run is applied in **batches of 250** pages, parents before children, each batch its own transaction, as background work with progress. Twins that a later batch needs as link targets are made first as invisible rows (PUB-514), so every link of an earlier batch resolves. The preview says the run will be visible in steps, and how many. *Why:* one transaction of many thousands of pages would hold locks and old rows for minutes (12). *Edge cases:* a run that stops halfway (a node dies, the room runs out) leaves each batch either done or untouched, shows what was done, and can be resumed, which continues with the same versions (PUB-1061). *Proof:* a test that kills a run after one batch and resumes it.
- **PUB-452** · new · **One run per pair** at a time (decided, PUB-1421). A single-page release asked during a whole-space run waits behind it, and the screen says so; approval releases (08) wait in the same queue, in order. *Why:* two runs would race on the same tree. *Proof:* a test of two runs started together.
- **PUB-453** · new · Every run ends with a **report**: what was released, taken off, skipped and why, the files copied, and the time; the report stays with the run on the release screen's history (13). The releaser is told when a background run ends (PUB-822). *Proof:* a test of the report's content.
- **PUB-454** · new · A run checks the releaser's rights at its start and again **before each batch**; when the rights are gone (the person was disabled, lost `space.release` or lost view of the published space), the run stops with what was done and says why. *Why:* the rule of scheduled publishing in Diffluence: rights at the moment of acting (spec 011, D16). *Proof:* a test that disables the releaser between batches.
- **PUB-455** · new · A run can be **cancelled** while it waits or between batches by the releaser or anyone with `space.release`; batches done stay done. *Proof:* a test.
- **PUB-456** · later · **Undo a run**: put back the twins' previous versions and places as a new run. It is possible because every twin keeps its versions; it is later because teams can release the earlier draft versions by restoring them in the draft. *Why:* a staging CMS offers rollback of a published workspace (02); worth it when asked.
