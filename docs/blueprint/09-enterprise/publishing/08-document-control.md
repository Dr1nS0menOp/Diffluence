# 09.P8: Document control: approval releases

How to read this chapter: see [01-draft-and-published-spaces.md](01-draft-and-published-spaces.md).

Document control (spec 064) and a pair meet in the draft space. A workflow governs draft pages there, as in any space: readers of the draft space see the approved version, writers see the working version. A pair adds one thing: what is approved can go to the published space, and the roadmap asks that approval itself can do that ("can follow a workflow, so approval publishes"). DOC-431 promised that this feature reuses the visibility rule of DOC-300; this chapter says how.

What DC1 built and DC2 is building matters here: DC1 gives `page_control` with the approved version as the page's current version, states with kinds, transitions, rounds and system steps with a cause; DC2 adds reviewers, rules to pass, independence, the workflow editor form and the review panel. Signatures come in DC4 and read and understood in DC5.

## 8.1 What can be released

- **PUB-700** · new · Of a controlled draft page, a release takes the **approved version**, never the working version, by hand or by approval (decided, PUB-1414). *Why:* DOC-1406, readers can only rely on approved content; a release is a distribution to readers (ISO 9001 7.5.3.2 a). *Edge cases:* because DC1 keeps the approved version as the page's current version, "the current version" in a release already means the approved one; the release path still checks the control row, so a later change of that storage choice cannot release a working version. *Proof:* a test that a release of a page in review sends the approved version; a mutation that takes the head version must be caught.
- **PUB-701** · new · A controlled page that was **never approved** has status **Cannot be released (never approved)**, and is skipped by every run. *Proof:* a test.
- **PUB-702** · new · A controlled page whose approved version is released and which has a newer working version in review has status **Waiting for approval**, not Changed since release, because releasing it now would change nothing. *Why:* the release screen lists only what a release would change. *Proof:* a test.
- **PUB-703** · new · Workflows are **refused in the published space** (PUB-220): control happens in the draft space, and the published space only holds what was approved there. *Why:* two procedures over one document would give two answers to "is this approved?" (DOC-411). *Proof:* a test.

## 8.2 Approval releases

- **PUB-710** · new · A workflow state of kind *approved* can be marked **"release when approved"** in a paired draft space, by those with `space.workflows` there and `space.administer` (so the person who turns it on could set up the pair). It is part of the workflow's definition, so it is versioned and audited like any change of the workflow (DOC-110, DOC-112). *Why:* one act, the approval, changes what readers see. *Edge cases:* the mark is ignored, and the editor says so, when the space is not paired, so a workflow copied from another space does nothing unexpected. *Proof:* a test of the validator and of the editor's message.
- **PUB-711** · new · When a page **enters** a state marked so, the system releases that page in the same queue as other runs (PUB-452): a single-page run, recorded with the actor "approval", the person whose answer passed the round as the cause, and the round's id. It runs after the transition commits, as background work, so a failing release never undoes an approval. *Why:* the approval must stand whatever happens to the copy (DOC-1250, a transition is one transaction); the release follows. *Edge cases:* the run uses the release path's rights, not the approver's: approving needs no right to release, because the pair's administrator chose that approval releases. Placement, links and files follow chapter 05 and 06 like any release. *Proof:* a test that approval makes a run whose author is "approval" with the approver as cause; a test that a failing release leaves the page approved and the status Changed since release, with the reason.
- **PUB-712** · new · Returning to the approved text without review (DOC-1410) does not release again, because nothing differs from what was released. *Proof:* a test.
- **PUB-713** · new · A **whole-space release** in a controlled space releases every page at its approved version, so a release manager can still release the space at a product date with approval having happened earlier; pages never approved are skipped and listed. *Proof:* a test.
- **PUB-714** · new · The pair can be set to **"only approval releases"**: then manual release of controlled pages is refused, and only approval releases them; taking off stays manual. Ordinary pages of the space, where the space workflow does not govern their kind, are released by hand as usual. *Why:* regulated teams want the release to be the approval and nothing else. *Proof:* tests for controlled and uncontrolled pages.

## 8.3 Withdrawal and obsolete versions

- **PUB-720** · new · When a controlled draft page is **withdrawn** (moved to a state of kind *obsolete*, DOC-322), its twin is **taken off** the published space at once, by the system, with the withdrawer as the cause. *Why:* readers must not keep relying on a procedure that no longer applies (ISO 9001 7.5.3.2 d, prevention of unintended use of obsolete information). *Edge cases:* this is not a setting: it happens in every pair, because the alternative leaves a withdrawn procedure in front of readers. *Proof:* a test; a mutation that skips the take-off must be caught.
- **PUB-721** · new · When a new version is approved, the previously released version becomes an older version of the twin, readable in its history only to those who may see history in the published space, as any older version (DOC-320 applies in the draft space; the twin's history is ordinary). *Proof:* a test.

## 8.4 What readers see of the approval

- **PUB-730** · new · A twin of a controlled page shows readers, near the title, **approved on** the date, and **version N**, where N is the twin's version number, so a reader can cite it. The name of the approver is shown when the pair's setting "show approvers to readers" is on (off by default). *Why:* ISO 9001 7.5.2 a asks for identification, including a version; who approved is often confidential to the team. *Proof:* tests of both settings.
- **PUB-731** · new · Once signatures exist (DC4), a twin of a signed version shows the **signature manifestations**: the printed name, date and time, and meaning of each signature, as text in the band and in PDF and Word exports' control block (DOC-531). The signature records stay in the draft space and are never copied (DOC-1202). *Why:* Part 11 §11.50(b) asks that the name, date and time, and meaning appear in any human-readable form of the record; the published copy is such a form. *Edge cases:* the manifestation is shown even when "show approvers to readers" is off, because a signature without its name means nothing; a pair whose team does not want names shown should not sign, and the setting's help says so. *Proof:* tests of the band and the exports, after DC4.
- **PUB-732** · new · The release stores, with each twin version, the **content hash** of the draft version it came from (DOC-1303) and the link mapping of the release. Verifying a twin maps its links back to draft ids and compares the hash: "This published text is the approved text." People with `space.audit` in the draft space can run it on one page or a whole space. *Why:* Part 11 §11.70 binds a signature to its record; the twin's text differs from the draft's only by rewritten links, which the mapping makes exact. *Proof:* a test that a twin verifies, and that changing a twin's stored document in the database makes verification fail.
- **PUB-733** · later · **Read and understood** (DOC-820) for a pair: confirmations are given by readers on the twin, recorded against the approved draft version it came from. It waits for DC5. *Why:* readers are in the published space; the record belongs to the controlled document.
- **PUB-734** · later · **Periodic review** dates (DOC-800) stay in the draft space; a twin may show "next review" to readers once DC5 exists, if teams ask.
