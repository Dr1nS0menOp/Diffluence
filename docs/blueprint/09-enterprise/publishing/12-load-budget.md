# 09.P12: Load budget

How to read this chapter: see [01-draft-and-published-spaces.md](01-draft-and-published-spaces.md).

Every feature states what it costs (ARC-238), measured on real data, not on generated data (wave PF). The installation must keep room for four times its database work (ADR-036). The design of this feature puts its cost where it is rare: reading a published page costs nothing extra, because a twin is an ordinary page (PUB-203); a change in a draft space costs one small write; a release costs about what publishing the same pages costs, plus copying changed files.

The figures used: publishing measured 143 pages a second on an empty space and 70 at 50,000 pages, p95 121 ms, six at once (`docs/operations/limits.md`); the real-data dump of wave PF has 5,962 pages; opening a page there takes 6.4 ms, a controlled page as a reader 8.0 ms (DC1 report).

- **PUB-1100** · built · **Reading a twin** adds no query and no join: the query-count budgets of ARC-239 for opening a page, the tree, search and the bell stay as they are for the published space. The managed rule is read only on write paths, from the space row they already load. *Proof:* `internal/app/query_budget_test.go` runs its screens in a published space with unchanged numbers; a mutation that adds the pair check to the read path changes a count and fails.
- **PUB-1101** · partly · **Reading a draft page** as a writer adds at most **one query** by primary key for the release status of the band (the page pair), or none when joined into the page's load; budget **within 1 ms** of an ordinary page on the real-data dump. *Proof:* the query-count test with a budget raised by one for a draft page, with this line as the reason; the benchmark.
- **PUB-1102** · built · **A change in a draft space** (a publish, a move, a label, a look change, a file) adds **one UPDATE** of the page pair in the same transaction, only for a page that was released (PUB-340, PUB-341); in an ordinary space it adds nothing. Budget: publishing in a draft space within **5%** of publishing in an ordinary space at the same size. *Proof:* a query-count test of a publish in both kinds of space; the benchmark of publishing.
- **PUB-1103** · new · **The release screen and statuses** of a draft space read the page pairs with the pages, in one query with an index on (pair, status), paged by 200 rows: budget **100 ms** for a space of 5,000 pages and **300 ms** at 50,000 pages, in the reading class of ARC-233. *Proof:* the benchmark on the dump and on the 50,000-page space of limits.md.
- **PUB-1104** · new · **A preview** reads the page pairs of the scope, the files' sizes, and the links of the documents in scope (for links that stay text, PUB-430). Budget: **2 s** for 1,000 changed pages; past that the preview runs as background work and the screen shows its progress. It is in the search-and-reports class, so a large preview never takes a saving connection. *Proof:* a benchmark; a test that a preview of 2,000 pages runs as background work.
- **PUB-1105** · new · **A run** writes, per page, about what a publish writes (the version, the search entry, the tree row if new, the audit event) plus the link rewriting in memory and the page pair update. Budget: **at least 50 pages a second** on the dump, so a run of 1,000 pages finishes within **20 s**, and a single-page release within **150 ms** p95 without files. A run is background work in the worker, holding one connection; at most **two runs** at a time per node, whatever the number of pairs. *Why:* publishing measured 70 pages a second at 50,000 pages; a run should not be much slower than the publishes it replaces, and two runs take two connections of a pool of twenty, leaving the rest to people. *Proof:* the benchmark of a whole-space run of the largest space of the dump, paired (decided, PUB-1427); a test that a third run waits.
- **PUB-1106** · new · **One transaction up to 1,000 pages** (PUB-450) holds row locks only on the published space's rows it writes, which nobody else writes (PUB-220), and on the pair row; readers are never blocked (PostgreSQL's reads do not wait on row locks). Budget: the transaction lasts at most **30 s**; a run whose preview estimates more uses batches (PUB-451) even under 1,000 pages. *Proof:* a test with a slowed run that it switches to batches; the benchmark's longest transaction.
- **PUB-1107** · new · **Files** are copied only when changed (PUB-320); bytes copied per run are the sum of the changed files, shown in the preview. Copying streams from storage to storage without holding a file in memory, as `attachments.CopyAll` does today. Budget: memory of a run stays under **64 MB** whatever the files' size. *Proof:* a test that copies a file of 1 GB and measures the process's memory.
- **PUB-1108** · new · **Budgets measured** on the real-data dump with its largest space paired and released (decided, PUB-1427): reading a twin equal to an ordinary page (within the noise of 0.5 ms); a draft page within 1 ms; publishing in the draft within 5%; the release screen within 100 ms; a single-page release within 150 ms p95; a whole-space run of that space at 50 pages a second or better; a second, unchanged whole-space run (nothing to do) within 2 s. The feed and search of a person who sees both spaces stay within their PF budgets plus 10%, since they see more pages. *Proof:* the benchmark, run in each wave of spec 073, and the next stress test on the server.
