# 09.P14: Migration and upgrade

How to read this chapter: see [01-draft-and-published-spaces.md](01-draft-and-published-spaces.md).

Nothing in an installation uses this feature yet, so there is no data to move. What needs care is threefold: the upgrade itself, under the expand and contract rules of blueprint 07 (a release must run beside the previous one on the same database); the experimental switch of ADR-043; and teams that already have a populated space and want it to become a published space.

## 14.1 The schema

- **PUB-1300** · built · The migration is **expand only**: new tables for pairs, page pairs, file pairs, left-out marks and runs; a column on nothing that exists except a nullable pair role on `spaces`, which the previous release never reads; the trigger of PUB-224, which does nothing while no space is published; and the split of `space.release` off `space.administer`. *Why:* the upgrade promise of blueprint 07. *Proof:* the N/N+1 upgrade test across the release.
- **PUB-1301** · built · The split of `space.release` uses the machinery of waves PM, FU and DC1 (`rbac_split_off`, `rbac_words`, `rbac_split_roles_from`, `SplitFrom` in Go, the templates, `WithSplitOff`, the bundle version): every holder of `space.administer` holds `space.release`, nobody else. *Proof:* the adoption test that snapshots every decision of `Evaluate` and the SQL lists before the migration and compares after: nothing changes except the new permission where the broader one was.

## 14.2 The experimental switch

- **PUB-1303** · built · The feature is an **experimental part** named `publishing`, off on a new installation and on every upgraded one, because no installation used it before (decided, PUB-1415). The migration of spec 069 that turns on parts that left a trace has nothing to find for it. While off, its routes answer 404 `experimental_off`, its screens and menu items are absent, and the space settings section shows nothing. *Why:* ADR-043 freezes new parts for 1.0 and makes optional parts experimental; this part is optional, new, and adds a write path into spaces, so it must earn its place. *Proof:* the tests of spec 069 extended with this part's routes.
- **PUB-1304** · built · Turning the part **off** while pairs exist keeps them as they are: the published spaces stay read-only (decided, PUB-1425), runs that wait are cancelled with a note in their report, and a running run finishes its current batch and stops. **Ending a pair** stays open while the part is off, as cancelling a restore does in spec 069, so an administrator can always give a published space back to its editors. *Why:* "an off part keeps what exists" (ADR-043); unlocking the published space would invite edits that the next release overwrites. *Proof:* tests of turning off with a pair, with a waiting run and with a running one.
- **PUB-1305** · new · Turning it **on** again brings back every pair as it was; statuses are as stored, and the consistency check (PUB-343) runs once. *Proof:* a test.

## 14.3 Older nodes during an upgrade

- **PUB-1306** · partly · During an upgrade a node of the previous release can run beside the new one. It does not know the managed rule, so it would let an editor write into a published space. The **trigger** (PUB-224) refuses that write in the database, and the old node shows its ordinary error. Turning the part on for the first time is refused during the grace period after the upgrade that brought it (wave O2), when the previous release may still run, so in the normal case no pair exists while an older node runs; the trigger covers the rest, such as a rollback. *Why:* the guarantee of PUB-220 must not depend on every node being new. *Edge cases:* Diffluence keeps no list of running nodes and their releases today; if the grace period cannot be read reliably, the trigger alone carries this line, which is enough for safety and costs only a clear error for the old node's user. *Proof:* the N/N+1 test with a pair: the old binary's edit of a twin fails with the trigger's message.
- **PUB-1307** · new · **Rolling back** to the previous release after pairs exist leaves published spaces read-only through the trigger, and the old release has no screen for them; the release notes say so. Rolling forward again finds everything as it was. *Proof:* a rollback test.
- **PUB-1308** · built · No **contract** migration is needed for this feature. *Proof:* none.

## 14.4 Existing spaces

- **PUB-1302** · new · **Start a draft space from this space**: for a populated space that should become a published space (scenario S4), a person with `space.administer` there and `create_space` makes a new draft space from it in one step. The step copies every page, folder and link at its current version with their files, labels and look (not comments, restrictions, watchers or history, as PUB-1406 and PUB-1405 say), pairs every page with its source **in step**, and makes the existing space the published space of the pair. The new draft space receives only those grants of the existing space that include writing (`page.create`, `page.edit` and the permissions split off them, and `space.administer`), never grants that only view, so readers of the existing space do not see drafts. *Why:* a team should not have to empty its space to start; giving the draft space only the writers' grants keeps the separation from the first minute. *Edge cases:* pages under view restrictions in the existing space are copied with their restrictions into the draft space, so nobody who could not see them before sees their drafts, and their twins keep their restrictions; blog posts and databases stay in the existing space as they are, and the preview lists them, because they are not released (PUB-231, PUB-232) and the existing space becomes read-only for them too. *Proof:* tests that every page is paired in step, that a reader of the old space cannot see the draft space, and that a restricted page stays restricted on both sides.
- **PUB-1309** · new · The preview of PUB-1302 says what changes for whom, in numbers: the people and groups who will no longer edit the existing space and will edit the draft space instead, the posts and databases that become read-only, the files that will be copied with their size against the new space's room, and how long it is likely to take. Large spaces run it as background work with progress, like a run. *Proof:* tests of the preview.
- **PUB-1310** · new · Links between pages of the existing space keep working there; in the draft space they are rewritten to point at the draft copies, so the draft space's links stay inside the draft space, and the release maps them back. *Why:* without this, writers in the draft space would follow links into the published space and edit nothing. *Proof:* a test that the draft copy's links lead to draft pages.
- **PUB-1311** · new · Starting a draft space can be **undone** until the first release: ending the pair then offers to delete the draft space, and the existing space is ordinary again. After the first release, ending the pair follows PUB-243. *Why:* a safe trial, as DOC-1107 gives for workflows. *Proof:* tests of undo before and after the first release.
- **PUB-1312** · new · The upgrade guide (`docs/operations/upgrade.md`) and the operator guide gain a section on the part: what it is, that it is off, how to turn it on, what the trigger refuses, and how to end a pair. *Proof:* review of the guide in the wave.
