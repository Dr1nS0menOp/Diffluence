# Wave Y: replacing the master key

Report of the build of spec 034, on 8 November 2026.

## What was built

- **Key ids.** A sealed value now starts with format 2 and an 8-byte id of the key that sealed it, an HMAC of a fixed text under the key. Format 1 values still open: every loaded key is tried, and GCM refuses a wrong one.
- **Several keys at once.** `internal/keys` loads `master.key`, and beside it `master.key.next` and `master.key.previous` when they exist. Only the key in `master.key` seals; the others only open.
- **A root that stays.** Fingerprints and the signing key are derived from a root. A 32-byte key file is both root and KEK. After the first change, the file holds `DFK2`, the root and the new KEK, so login fingerprints, audit checkpoints and bundles keep working.
- **Commands.** `diffluence key add`, `promote`, `reseal`, `check [--deep] [--require-current]`, `retire`. Each step can be run again after a crash, and refuses while an earlier change is unfinished. Each is audited with the key id only.
- **Resealing beside a running instance.** A value is replaced only when it still holds what was read, so a value written meanwhile wins. Files are decrypted and encrypted again with a new data key, replacing the old file whole. What does not open is skipped and counted, so the job always ends.
- **Cursors.** The encryption job of spec 032 and the reseal job remember the last file they finished in `storage_state` (migration 0034), and each run finishes at least one file.
- **Backups.** `backup.sh` takes `master.key.next` and `master.key.previous` along when they exist; `restore.sh` puts them back and ends with `diffluence key check`.
- **Restore drill.** It starts a key change, backs up halfway, restores, proves with `key check --deep` that everything opens, finishes the change, and downloads the file again with only the new key.
- **A guard.** `TestEverySealedColumnIsKnown` fails when code seals in a new place that the reseal and check do not know.

## Tests

Failure paths first. In `internal/keys`: a value of a key that is not loaded, a changed key id, key files of a wrong length, a damaged next key, values from before key ids, a promote run again after a crash, a second change while the first is unfinished, a promote that would overwrite an older key. In `internal/storage`: a file sealed again under the new key, a file of a retired key that does not open and is left alone, a plain or damaged header. In `internal/app`, against PostgreSQL: a missing key file, a wrong key (named for every value and file without showing them), a file copied under another name, damage inside a file that only a deep check finds, a retire refused before resealing, a value changed while it is sealed again, a value that does not open and a reseal that still ends, the encryption cursor, and the whole change while the instance serves a download.

Nine new mutations, all caught. One first went unnoticed because the mutation script applies expressions with JavaScript, whose `replace` changes the first match only; it now uses `replaceAll`.

## Measured

Nothing new. Resealing reads and writes each file once, so its cost follows the 226 MB/s measured for encrypted files in spec 032.

## Not proven

- Several nodes changing keys one at a time: reasoned, and tested only as files on one machine.
- A Kubernetes secret: the guide says what to place, but no cluster ran it.
- A store of millions of files: the cursor is tested on three.
- Listing still reads the whole store on every run.

## Left

- Replacing the root, for when the key file itself was stolen (SEC-714).
- Reloading keys without restarting a node.
- Unsubscribe links in mails sent before a change stop working once the old key is retired.
- S3 storage is not built, so resealing works on the disk store only.

## Notes for the next session

- Migration 0033 is a reserved placeholder for wave X. Remove it if wave X brings a real 0033.
- The mutation script evaluates expressions with JavaScript: use `replaceAll` when a text occurs more than once.
