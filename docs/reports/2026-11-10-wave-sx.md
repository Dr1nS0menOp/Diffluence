# Report 2026-11-10: wave SX, the security wave of ADR-038

Branch `wave-sx`, spec 046. Written for the next build session.

## What was asked

ADR-038 gave three security items: a witness of the audit log outside the database with checkpoints every five minutes, a stop on password login after 100 wrong passwords in a row, and Semgrep, CodeQL and a ZAP baseline in CI.

## What was built

- **The witness.** `audit.SignCheckpoint` returns the checkpoint and skips a head that is only the record of the last checkpoint. The job runs every five minutes. `App.signCheckpoint` writes the checkpoint to the application log after the commit, through a logger whose handler answers "enabled" for every level, so a quiet log level keeps it. `audit.ReadWitness` takes the lines out of any log, also after a prefix; `audit.CompareWitness` checks signature, prune anchor, tail and hash per checkpoint, a thousand per query. `diffluence audit verify --witness FILE|-` ties them together and audits the result. ADR-039 records the change to ADR-013.
- **The stop.** Migration 0042 adds `failed_logins_in_row` and `password_locked_at` to `local_credentials`. `Login` reads them with the account. A wrong password on a live account counts in one `UPDATE … RETURNING`, in the transaction of the failed-login event, and the hundredth sets the stop, records `auth.password_locked` and sends the mail `password_locked` once. While stopped, the hash still runs and every answer is the answer to a wrong password. A right password ends a run; `storePassword` ends a stop for every new password; `POST /api/v1/admin/users/{id}/unlock-password` (administrator, audited as `auth.password_unlocked`) and a notice with a button in the user dialog of the console lift it.
- **Scanners.** Jobs `semgrep` and `codeql`, and a ZAP baseline in the job `container` against the image it just built, with `.zap/rules.tsv`. Details and every finding are in spec 046.

The local scans of ZAP need a host name with a dot as the public address, because the passkey settings refuse a bare name. CI uses `localhost`, which they accept.

## The real bug the scanners found

`isTextFile` in `web/src/components/file-preview.tsx` used `/^text\/|json|xml|yaml/`. Its `|` binds loosest, so `xml` anywhere in a type matched, also in `application/vnd.openxmlformats-officedocument.wordprocessingml.document`. A Word or Excel file therefore got a text preview in the file dialog and on the file page, which showed its bytes as text and kept the office viewer from opening. It was not a weakness: the bytes were shown as text, never run. The pattern now matches the whole type; the test failed first.

## Not proven

- The three scanner jobs in GitHub Actions: nothing is pushed. The same versions, rules and queries ran here and end clean; the Actions wiring (the ZAP action, the CodeQL upload and permissions, Semgrep in a job container) shows on the first push.
- Semgrep's registry rules are fetched at run time, so a new rule can turn the job red without a change here. That is the point of the job, but it can surprise a push.
- A real log server keeping the witness lines, and a passkey login after the stop in a real browser (proven at `OpenSession`, which the passkey route calls). The end-to-end server cannot reach 100 wrong passwords inside its own limits, so there is no browser test of the stop.
