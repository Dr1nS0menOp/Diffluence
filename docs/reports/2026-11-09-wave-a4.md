## Measurements

- **Reads that may lag.** In the same mix of reads in the test database (50 page views, 20 trees, 10 searches, 10 feeds, 10 notification lists, 5 people lists), 170 of 1,675 queries are marked as may lag: 10.1 %. Before this wave, none were. Page views and trees dominate that mix and must stay current; the gauge shows the real share in use.
- **Cost of the mark.** 6.1 ns per query (Go benchmark), against roughly 0.3 ms per query in the mix.
- **Helper check.** Once a minute, at most three HTTP requests of at most five seconds each, then one short transaction. Nothing on a request path but one query in `/system/capabilities`.
- **File details.** One permission check per page among the files asked, not per file.

## Proof

- Go: `TestAHelperThatDoesNotAnswerIsShownAndNoLongerOffered`, `TestOnlySomeoneWhoMayAddFilesIsOfferedToSaveAChangedPDF`, `TestOnlyListsAndHeavyReadsMayLag`, `TestTheCounterSeparatesReadsThatMayLag`, `TestAReadIsCurrentUnlessMarkedAndCurrentWinsInside`, and a reader refused when closing comments in `TestACommentIsCheckedAndStaysBehindItsPage`.
- Frontend: `capabilities.test.ts`, `frame-messages.test.ts`, `craft-frame.test.ts`.
- Browser: "a PDF changed in the viewer is kept as a new version, and only what the frame sends counts". It saves from inside the frame the way PdfCraft's bindings do (a blob address and a link with a `download` name), checks that a message posted by the page itself is ignored, that bytes that are not a PDF are refused, that a kept PDF becomes version 2, and that a reader gets no button.
- Five new mutations, each caught: a write marked as may lag, a helper that does not answer still offered, a viewer offered to save, any window posing as a frame, and bytes that are not a PDF kept.
- `make check`: passed. `scripts/e2e`: 426 passed, 6 skipped (16.0 min). Full mutation check: all 392 caught (45 min, `MUTATION_JOBS=4`). A first full run found that dropping the "reads only" rule was not caught, because no test wrote to a listed path; the test now does, and the second run caught it.

## Not proven

- The browser test does not press PdfCraft's own save button: its canvas has no element to press. It drives the same three steps PdfCraft's shipped bindings use. If a later PdfCraft saves another way, the download still works, and the offer to keep it does not appear.
- The editing service check uses its `/livez`; no test runs with the editing service down.
