# Wave RV5: the module boundary as a check, and smaller fixes

Builder report for spec 072. It covers what was built and proven in this wave.

## The module boundary (ARC-027)

**What was built.** `internal/db/boundary_test.go` and `internal/db/boundary_list_test.go`:

- every table and view the migrations create has one owning module; a new table without one fails;
- the SQL of every Go file outside tests, below `internal/` and `cmd/`, is read through `go/parser`, so only string literals count, never comments;
- a table counts when it follows `FROM`, `JOIN`, `INTO`, `UPDATE`, `USING` or `TABLE`;
- each pair of module and foreign table is listed with its exact count, under a comment that says why. More fails, and so does less, until the number is lowered.

**The numbers.**

| | Mentions | Pairs |
|---|---|---|
| Before | 564 | 201 |
| After | 557 | 195 |

The biggest readers of other modules' tables: `blocks` (86, one query per dynamic block), `pages` (63, of which `spaces` 26 and `users` 23), `app` (40, the upkeep of the installation), `console` (42), `exchange` (45, whole spaces in one transaction), `permissions` (41, the facts the rule decides from). The most read tables: `users`, `pages`, `spaces`.

**Moved behind the owner.** Five reads, each through a small exported function that takes a `db.Querier`, so no wiring changed and the caller's transaction stays:

- `settings.Load` for `analytics` and `automation`; `settings.Service.ReadIn` uses it too;
- `pages.Title` for `webhooks`;
- `spaces.HomePage` for `sharing`;
- `backups.ReadinessToRestore` for `restore`;
- `restore.Leave` for `cmd/diffluence`.

Each new function has its own test in its package, written before it. The callers' behaviour is covered by the existing suites in `internal/app` (webhook titles, guest invitations, restore refusals, analytics and automation settings), which ran unchanged in `make check`.

**What was looked at and kept.** `labels` cannot ask `pages` or `spaces` (both import it), and `comments` cannot ask `pages` (pages imports comments). `presence` builds one stamp from four modules on a polled path, where one query is the point. These stay listed with that reason.

## One check of the editing connections at a time

`collab/access.mjs` now runs one recheck at a time, and every call that arrives during a run shares one more run after it. The test fires ten rechecks during one slow run: the API is asked twice, not ten times. Both new tests failed against the old `access.mjs` and pass now.

## The owner's password off the command line

- `deploy/backup/backup-service.sh`: `as_owner` runs `psql` and `pg_dump` with the address minus its password, and the password, percent-decoded, in `PGPASSWORD`. Checked by hand in the toolbox with an address whose password holds `@`, `/`, `%` and a backslash, one without a password, and one in the `key=value` form.
- `cmd/diffluence/restore.go`: `passwordApart` does the same for `psql` in a restore, with a unit test.

## Migrations

- `docs/development.md` explains why placeholder migrations exist and why they stay.
- `TestAContractMigrationRemovesAColumnOnACopyOfAnInstallation` runs a contract migration end to end on a `CREATE DATABASE … TEMPLATE` copy of an installed database with data. It runs in `make check` and in CI's `go` job.

## `master.key`

The install guide says to keep the key apart from the data on installations outside Compose, through `DIFFLUENCE_MASTER_KEY_FILE`, and why Compose keeps it in the data volume.

## Mutations added

Nine, in `scripts/mutation-check.sh` under "Spec 072": a new crossing in a module, the check counting the SQL of tests, a view without an owner, the password left in the address, a failed backup restorable, a leaving node still busy, a stored choice not read, and two in the editing service (every recheck at once, rechecks during a run dropped).

## Not proven

- `as_owner` in the backup service has no automated test: the script runs its loop when sourced. It was checked by hand, and the nightly restore drill runs it.
- That no process in the backup container can read `PGPASSWORD` was not tested; it rests on Linux allowing `/proc/<pid>/environ` only to the same user and root.
- The check sees only upper-case SQL, and not a second table after a comma in `FROM`. A search found neither form today.
