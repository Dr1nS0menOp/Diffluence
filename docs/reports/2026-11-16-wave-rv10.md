# Wave RV10: administration changes need a signed-in session

Builder report for spec 085. It covers what was looked at, built and proven.

## What was looked at

Whether a route below `/api/v1/admin/` takes a personal access token was decided per route: by wrapping its rule in `SessionOnly` or `Sensitive`, or not. The route table on main `6ef6719` lists 142 routes below the prefix: 86 change something and 56 read. 13 of the changes followed only the `admin` scope of spec 015 H9.

## What changed

- `Router.Handle` passes every rule through `withAdministrationRule` before it records and enforces the route. A pattern below `/api/v1/admin/` whose method is not `GET` or `HEAD`, or that has no method, becomes session-only. A rule that is already session-only or sensitive keeps what it has.
- The prefix is one constant, `adminPathPrefix`, used by the router and by `scopeFor`.
- `docs/api/routes.txt` and `openapi.json` were regenerated: 13 lines change from `permission:administrator` to `session-only permission:administrator`. No route was added or removed.
- Your account, Tokens: the scope reads "Administration, read only", and the help text says only a signed-in session changes Administration.
- Docs: ARC-140, spec 013 D12 and AC-12, spec 015 H9, `docs/api/README.md`, and ADR-052 in the decision log.

## How the tests prove it

| Test | Proves |
|---|---|
| `TestEveryAdministrationChangeNeedsASession` (`internal/app`) | Walks the real route table with a token holding every scope, owned by an administrator: every route below `/api/v1/admin/` that is not a read answers `403 session_only` (86 walked); the same token still reads `GET /api/v1/admin/features`; a session still changes features |
| `TestAnAdministrationChangeIsSessionOnlyWhateverRuleItWasGiven` (`internal/httpapi`) | The rule for `PUT`, `DELETE`, a pattern without a method, a rule already session-only or sensitive, `GET`, `HEAD`, and routes outside the prefix (also one that only starts with the same letters) |
| `TestTheRouterEnforcesTheSessionOnlyRuleOfAnAdministrationChange` | The rule the router enforces is the one it lists |

## Seen failing

Both new test files were written first and run against the code of main: the walk failed on exactly the 13 routes, and the router tests failed on the changes and the pattern without a method.

## Mutations

Four new lines under "Spec 085" in `scripts/mutation-check.sh`: the rule dropped from `Handle`, only `PUT` counted as a change, reads made session-only too, and a pattern without a method let through.

## Decisions taken on the product owner's behalf, may be overruled

- RV10-1 (ADR-052): every change below `/api/v1/admin/` needs a signed-in session; the `admin` scope keeps reading.
- RV10-2: the rule is applied in the router at registration, so `routes.txt` and `openapi.json` show the rule that is enforced, rather than a second check at request time that the table would not show.

## Not proven

- Routes outside `/api/v1/admin/` keep the rules they were registered with; this wave does not look at them.
- `make check` is not green: `TestMatrixSQLAgreesWithEvaluate` in `internal/permissions` hits the 45-minute limit, waiting on the database. The package is the same as on main. Its last change came from wave RV9, which added `perm_page_readers` to the test. Whether it also stops on main has not been run.
