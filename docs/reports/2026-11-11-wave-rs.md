# Wave RS: restoring over the live installation from the console

Spec 059. Decided by the product owner on 2026-11-11, planned in spec 058, section 3.2.

## What is built

- **The console:** Administration, System, Backups gets a section "Restore over this installation".
  - Choosing a complete backup shows in plain words what is lost and that a safety backup comes first.
  - The installation's name must be typed out, and the button stays off until it is.
  - A second factor is asked: a code from the authenticator app, a recovery code, or a passkey confirmed in the session within 10 minutes.
  - The section shows where the latest restore stands, and a requested restore can be taken back before the worker begins.
  - It shows the command an operator uses without the console.
- **The routes:** `POST /api/v1/admin/backups/restore` (sensitive, administrator, plus the second factor) and `DELETE /api/v1/admin/backups/restore`.
- **`internal/restore`:** the state machine (`requested`, `preparing`, `stopping`, `backing_up`, `restoring`, `checking`, then `done`, `refused` or `failed`), and the `Runner` that moves a restore along step by step behind a `Steps` interface.
- **Migration 0049:** the schema `ops` with `ops.restores` and `ops.nodes`, which a restore never touches, and `sessions.reauth_method`. Everything in it may run twice.
- **The nodes:**
  - Every node says every 5 seconds that it serves, and stops within 5 seconds once a restore begins.
  - A node that starts says so, and never serves during a restore.
  - A waiting node shows a public page that names the step but no backup, date or person, and the way back when the restore failed.
  - `/readyz` answers `restoring` or `restore_failed`.
- **The worker:**
  - `diffluence backup next` hands it a restore before any backup, and `backup restore-prepare | restore-run | restore-abort | restore-way-back` carry it out.
  - The backup service script makes the safety backup between them, and keeps every backup while a restore runs.
  - `docker compose run --rm backup way-back` is the way back.
  - `diffluence backup restore-request` asks for a restore from the command line.
- **Backups:** they hold the tables of `ops` without their rows, in the service and in `scripts/backup.sh`.
- **`compose.yaml`:** the backup service writes the data volume, and gets the owner's database address and `DIFFLUENCE_DATA_DIR=/data`.
- **The restore drill:**
  - Step 6 restores for real in a throw-away project with its own images, after a tampered backup is refused while the nodes keep serving.
  - Step 7 cuts a backup's files short so the restore stops halfway, checks that the nodes wait and the page names the way back, and runs `way-back`.
- **Docs:** `backup-restore.md`, the changelog, OPS-118 built, spec 058 points to 059, and a roadmap item for restoring one space.

## What the drill found

The first two drill runs stopped in the files: `tar` changes the mode of the folder it unpacks into, and the backup service may not change the data folder it does not own (it has only `CHOWN` and `DAC_OVERRIDE`). It now unpacks into a new folder inside the data folder and moves everything up, then hands everything to the server's user. Both times the database had been restored in its single transaction, the nodes waited, and the waiting page named the way back, as designed.

The third run passed the real restore (step 6) and found a second fault in step 7: after a restore stopped in the files, the data folder no longer held a `master.key`, and the guard that keeps the worker from emptying a wrong folder then refused the way back. The files step now leaves a mark (`.restoring`) while it works, and the guard accepts a folder with a `master.key` or that mark; `TestTheFilesStepEmptiesOnlyADataFolder` keeps the guard.

## Decided, and why

See spec 059, D1 to D16.
- **The state lives in its own schema.** The restore leaves out `ops`, and backups hold its tables without rows.
- **The database is restored in one transaction** that drops and makes `public` again.
- **The daily limit stays a constant**, not a setting: a stolen session must not be able to raise it.
- **Restoring one space** goes on the roadmap.
- **The command line skips the second factor:** shell access to the installation is more than the second factor.

## Not proven

- A Kubernetes Job as the worker.
- Several app nodes on several machines.
- A node paused for a long time that wakes up during a restore; ending other sessions covers it on paper.
- The time a large restore takes (wave 7, on the server).
- An administrator who logs in only through the identity provider must add a passkey to restore; that path is not tried in a browser.

## Seen in passing

In drill step 5 the weekly restore check says "the console could not be told the result of the restore check". That message is from spec 058's `restore-check.sh`: in the drill, no installation runs in the base folder to report to. The check itself passes.
