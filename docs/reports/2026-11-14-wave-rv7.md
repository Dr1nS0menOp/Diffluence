# Wave RV7: witness reports from the owner of the tables, and three loose ends

Builder report for spec 077 and three smaller items. It covers what was built and proven in this wave.

## What was built

**Witness reports are recorded by the owner of the tables** (spec 077; `internal/db/db.go`, `internal/audit/console.go`, `cmd/diffluence/main.go`, migration 0067).

- `db.GrantApp` revokes `INSERT` on `audit_witness_checks` from the application role, beside `UPDATE`, `DELETE` and `TRUNCATE`; it still reads the table.
- Migration 0067 adds `recorded_by` (empty for every report already there) and the trigger `audit_witness_checks_stamp`, which sets `recorded_by` to `current_user` and `checked_at` to `now()` on each insert, whatever the insert names. 0066 holds the number of wave GT2.
- `audit.LatestWitnessCheck`, which the audit area and System health read, takes only reports whose `recorded_by` is the owner of the table, from `pg_class`.
- `diffluence audit verify --witness FILE --report` compares as before with `DIFFLUENCE_DATABASE_URL` and records the report with the owner's address: `DIFFLUENCE_MIGRATE_DATABASE_URL`, or the one address of an install that has only one (`ownerURL`, as `worker migrate` uses). Without either it refuses before it compares, and names the command for the backup service.
- `docs/operations/install.md` gives the timer's command for Compose: `docker compose logs --no-log-prefix backup | docker compose run --rm -T --entrypoint diffluence backup audit verify --witness - --report`.
- The text on the audit page is unchanged, so no design picture changes.

**The summary's disk warning follows the setting** (`internal/console/console.go`, `internal/app/app.go`). `console.NewService` takes the warn level as a function, read at every look, which the app gives as `a.thresholds().DiskWarnPercent`, the level System health and the band already follow. `DiskNearlyFull` takes the level; zero is the default of 10.

**The timing test** (`internal/app/events_test.go`). `TestARunningWorkerFollowsTheSwitchAndNotesTheDrain` read once, right after Anna's second mention arrived, whether all four consumers of the event log had passed an event. The notifications consumer gave her the mention; the other three run on their own and may pass the event later, which a loaded machine makes likely. It now waits for all four with `waitFor`, as it waits for the mention and the drain (spec 068, D34). No other fixed time is left in it.

**Faster `internal/app` tests.**

- `testutil.MainWithTemplate` (new `internal/testutil/template.go`) migrates one database the first time a test of the binary asks for a migrated one, and gives each such test `CREATE DATABASE ... TEMPLATE` of it. The database defaults that migration 0050 sets with `ALTER DATABASE ... SET`, which PostgreSQL does not copy, are copied from the catalog. The template lives in one process only and is dropped at its end: each test binary embeds its own migrations, so a mutated one never reuses what another built. `internal/app/main_test.go` opts in. Other packages keep migrating per test until they opt in with a `TestMain` of three lines.
- `make test-race` runs `scripts/test-race.sh`: the tests of `internal/app` are listed with `go test -list`, dealt round-robin over `TEST_SHARDS` processes (default 4), and run beside `go test` of every other package. The script checks that the shards together hold exactly the listed tests before it runs them; each regexp names its tests in full. The 45-minute limit stays per process.
- Measured and left alone: Argon2id costs about 120 ms a hash under the race detector here and dominates a few tests that create many people or log in many times (`TestSuccessfulLoginsAreNotRateLimited`, `TestGroupMentionsAreOffAndHaveALimit`). The parameters are `identity.DefaultParams`, not configuration, so cheaper ones would need a new setting or a hook in production code; not done. `t.Parallel()` was not added: 829 tests would each need a review for shared state, while separate processes share only the database server, as the packages already do.

## Not proven

- Where the server holds the owner's address too (`deploy/install-lxc.sh`, the HA scripts, a `compose.yaml` from before spec 070), the console shows what that role recorded; the guarantee of spec 077 is that of the split of roles, as for the audit tables and the signing keys.
- The command in Compose (`docker compose run ... backup audit verify --witness - --report`) was not run against a real Compose install: that needs the backup image, which this wave did not build. The test runs the same code with an application role and the owner's address.
- After the upgrade Audit shows no comparison until the first report of the owner; this was tried in tests, not on an upgraded installation.
- The shards were measured on this machine, pinned and unpinned (above), not on a hosted runner. With `internal/app` shorter, `internal/permissions` may be the longest package on a runner of four cores.
- `TestARunningWorkerFollowsTheSwitchAndNotesTheDrain` failed once under load before this wave and was not seen failing again; the wait removes the one read that could see three consumers behind, which is the likely cause, not a proven one.
- Other packages still migrate a database per test; they can opt in to the template later.

## Decisions

- Option A of spec 077 (the grant) over a signature with a key derived from `backup.key`: simpler, as strong as the split of roles that already protects the audit tables, and it works on installs without a backup service.
- Reports from before 0067 stay in the table and are not shown, rather than removed: the application role may still not delete, and the table keeps its history.
- The database stamps the time as well as the role, so no report can hold a time ahead of the others.
- The text on the audit page was not changed, to keep the design pictures; the operator documentation carries the new command.
- Faster tests through a template per test binary and processes per shard, not `t.Parallel()` and not cheaper password hashing; see above.
