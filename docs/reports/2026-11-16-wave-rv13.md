# Wave RV13: only the holder starts a rule outside its trigger

Builder report for spec 093. It covers what was looked at, built and proven.

## What was looked at

- `NewHook` in `internal/automation/service.go`: who may make a new incoming webhook address for a rule.
- `RunByHand` in `internal/automation/match.go`: who may start a rule by hand, and on which pages.
- `Incoming`, `RunSchedules`, `matchTrigger`, `Manual`, `Test`, `Update` and `Delete`: every other way a rule starts or changes.
- `internal/db/boundary_list_test.go` and the callers of `automation.Service`: whether any other package copies, imports or rewrites rules. None does; only the routes in `handlers_rules.go` call the service.

## What changed

- **`requireHolder`.** A small check on top of `holds` (spec 092) that answers `409 rule_held` to someone who does not hold a rule.
- **New address.** `NewHook` calls `requireHolder` after `Get`, before a token is made or stored.
- **By hand.** `RunByHand` calls `requireHolder` after `mayManage` for a rule whose trigger is not manual. A rule with a manual trigger stays open to everyone who can see the page.
- **Spaces.** `RunByHand` answers `404` when the rule does not reach the space of the page (`Definition.reaches`), which `Manual` and event runs already checked.
- The comment on `POST /api/v1/rules/{id}/run` in `handlers_rules.go` names the holder.
- No migration, no new route, no new text: the rule editor already shows the server's message.

## How the tests prove it

| Test | Proves |
|---|---|
| `TestOnlyTheHolderOfARuleMakesItsIncomingAddress` | Another space administrator gets `409 rule_held` on a new address; the holder's address still starts the rule; only one address change is audited; after a take-over they can make one |
| `TestOnlyTheHolderStartsByHandARuleWithAnotherTrigger` | Another space administrator gets `409 rule_held` starting a rule on comments by hand; no run is recorded and the page is not labelled; the holder gets `202` |
| `TestOnlyTheHolderStartsAnInstanceRuleByHand` | The same among administrators for a rule of the instance |
| `TestByHandAnInstanceRuleStartsOnlyInItsSpaces` | A manual instance rule given one space answers `404` on a page in another space, and labels nothing |

## Seen failing

All four tests were written first and run against main `56da378`: the new address answered `200` for someone else, both runs by hand answered `202`, and the run outside the rule's spaces answered `202`.

## Mutations

## Decisions taken on the product owner's behalf, may be overruled

- RV13-1 (spec 093 D1): only the holder makes a new incoming address; others take the rule over first.
- RV13-2 (D2): only the holder starts a rule of another trigger by hand; others take it over first. The answer is `409 rule_held`, the same as for a change.
- RV13-3 (D3): a manual rule stays open to everyone who can see the page, as built in spec 015, but only within the spaces its holder chose.
- RV13-4 (D4): no other path starts a rule as its holder; copying, importing or exporting rules does not exist.

## Not proven

- The body of an incoming call is not read, so it cannot steer the values of a step. No test proves that, because there is nothing that reads it.
- During a rolling upgrade a node of the previous release still makes addresses and starts rules by hand for someone who does not hold them.
