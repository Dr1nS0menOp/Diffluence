# Report: wave RV3a, a feature freeze for 1.0, a passkey after the password, and docs that say what is true (13 November 2026)

## What happened

Wave RV3a builds spec 069 and ADR-043, the product owner's answers of 13 November 2026, together with small fixes from the review of that day. How each answer is built was decided on the product owner's behalf, and may be overruled.

## What was built

- **Experimental parts start off.** Automation rules, databases, bundles between instances and restore from the console each have one switch for the installation, under Administration, Organising.
  - While a part is off, its routes answer 404 `experimental_off`, no screen offers it, and what exists stays.
  - Public sites and analytics keep their own switches, which already start off, and are marked experimental.
  - The example space leaves out its database while databases are off.
- **An upgrade keeps what was used.** Migration 0054 turns on each part that left a trace (`docs/operations/upgrade.md`).
- **The claim.** One node, a few hundred people, measured on your own hardware: in the README, the install guide and the known limits, with links to both stress tests.
- **Docs.**
  - `SECURITY.md` says alpha, as the README does.
  - The risks page and the threat model are brought up to date, with a table of what each control holds against which attacker.
  - The built ADRs are marked accepted.
- **Scopes by route.** A token's scope follows the pattern of its route, not words in the address.
- **No query put together at run time.** The key rotation and the backup mail hold their queries in full; a test guards the whole code base.
- **`compose.dev.yaml`** pins `postgres:16` by digest.
- **A passkey after the password.** An account whose second factor is a passkey is asked for it after its password, and the login page offers it.

## Decided on the product owner's behalf on 2026-11-13

- **The switch.** A part off answers 404 `experimental_off`, because for that installation it does not exist. The list of rules of a page answers empty instead, because every page asks it.
- **Off keeps what exists.** A rule stays and does not run; a database stays and can be edited; only new ones wait.
- **Existing switches.** Public sites and analytics keep theirs, as the directive asked; their routes answer as before.
- **Upgrade detection.** It goes by traces. A bundle export whose job was cleaned up leaves none.
- **The ADR statuses.** The decision log forbids editing a decision, not its status. ADR-043 records the change.
- **The targeted mutation check.** The list leaves out the folder `internal/app`, which would select every mutation that runs its tests. The changed mutation of the key rotation was run by hand.

## Not proven here

- The upgrade on a copy of a real installation; the detection was tested by running the migration again on prepared data.
- That a passkey step begun for one account cannot finish another's with a real assertion: the API test proves the refusal only with an empty assertion, and the browser test uses one account.
- That a token cannot turn an experimental part on: the route is session-only, as the route table shows, without a test of its own.
- That the list of rules of a page is empty while automation is off when rules exist: the test has no rule to hide, so a mutation there would not be caught, and none was added.

## Seen on the way

The first e2e run after pinning `postgres:16` recreated the database container of the worktree once, because its image changed, and every test of that run failed. The second run, on the pinned image, passed. Each development setup sees this once, when it first takes the pinned image.
