# Wave RV6: settings that let more through are a system administrator's, confirmed

Builder report for spec 076. It covers what was built and proven in this wave.

## What was built

**A confirmed change** (`internal/settings/guard.go`, `internal/httpapi/handlers_console.go`).

- Each guarded section judges a change against the section in force, inside the transaction that stores it, with the row locked: `Access.looserThan`, `Retention.shorterThan`, and for backups `backups.keepsFewer`.
- `PUT /api/v1/admin/settings/{section}` refuses such a change with `403 confirmation_required`.
- `PUT /api/v1/admin/settings/{section}/confirmed` is `Sensitive(Permission(system_administrator))`. Its handler checks the section first, then a second factor through `identity.ConfirmSecondFactor`, under the same limit per account as a restore.
- The backups module stores its own section (`backups.SetSchedule`, `SetScheduleConfirmed`) through `settings.StoreSection`, because only it knows the worker's defaults. `settings.SetSection` refuses the backup section, so no caller can store it past that module.

**The settings forms start from what holds.** `Settings.Section` read the section under the plain name, while `SetSection` stores it as `section.<name>`, so every form showed the defaults after a reload. With a check against what holds, an unchanged form would have read as a change back to the defaults. It now uses `ReadSection`.

**Fewer backups** (`internal/backups/schedule.go`, `internal/backups/held.go`, `cmd/diffluence/backup.go`, `deploy/backup/backup-service.sh`).

- A confirmed change below what the worker holds opens a row in `backup_schedule_requests` (migration 0062).
- `backup next --held FILE` loads what the worker holds to from `/backups/.diffluence-held.json`. `ConfirmFewer` shows a code, compares an entered one, or ends the ask. `Next` raises what it holds at once and reports it in `backup_worker.held_keep` and `held_interval`.
- The code is `restore.Gate.CodeOf("backup schedule confirmation code", nonce ‖ ask ‖ keep ‖ interval)`, compared with `Gate.Matches`. The 16 random bytes live only in the worker's file, so a code the server saw confirms nothing later, and the server cannot reset the count of wrong codes or the time the code was shown.
- The shell's `prune` asks `diffluence backup held` and keeps at least that many; it removes nothing when the file cannot be read.
- The backups page shows what the worker holds while it holds more, the ask, and the field for the code.

**A shorter audit retention.** `Retention.Lowering` holds the shorter time, its reason and when it holds; `settled` applies it from then on, in the console and in `settings.AuditDays`, which `diffluence audit prune` reads. An ordinary save keeps it and ignores what a form sends. `DELETE /api/v1/admin/settings/retention/lowering` takes it back.

**A restore.** `DELETE /api/v1/admin/backups/restore` is `SessionOnly(system_administrator)`. `/api/v1/admin/backups/restore/code` is in `openDuringMaintenance`.

Unit tests: `internal/backups/held_test.go` (the first round holds the more, raises at once and never lowers, a damaged file is never a fresh start, the code covers its random part, ask and values) and `cmd/diffluence/backup_test.go` (`backup held` prints 0, the number, or fails on a damaged file).

Existing tests that changed with the behaviour: `TestTheWorkerFollowsTheConsole` lowers through the confirmed route; two sign-up tests and `TestAnOperatorCanChooseAnotherRuleForASecondFactor` store their access section through `SetSectionConfirmed`; `TestTheAuditLogStaysAYearByDefault` now expects the refusal of a shorter time.

The browser tests: `backups.spec.ts` asks for the second factor when fewer backups are saved and stores nothing without it; `people.spec.ts` shows the reason and the code for a shorter retention, the waiting time, and taking it back; its helper that puts a setting back uses a system administrator with recovery codes, because putting a stricter rule back is now a confirmed change.

## Seen failing

The tests were written beside the code, not strictly before it. To see each one fail, the mutation check puts the old behaviour back one rule at a time (36 mutations under "Spec 076"): for the restore, the maintenance list and each refusal of the settings it is exactly the code before this wave. Every one of them turned a test red; see Gates.

## Gates

All on main `ba17a33`, after DC2 and EV2 landed.

- `make check`: passed. The first run found migration 0062 failing when it runs a second time, as every migration since 0049 may; it now uses `IF NOT EXISTS`, and `TestTheBackupServiceWaitsForABackupBeforeAnUpgrade` passes.
- Targeted mutation check (`MUTATION_CHANGED`, `MUTATION_JOBS=2`, without `internal/app` and the script): 261 run, 260 caught. The one left was a mutation of this wave that did not compile (`return false` left a variable unused); it now reads `return (fewerKept || lessOften) && false`, and was run by hand on a copy of the tree: `TestKeepingFewerBackupsNeedsASystemAdministrator` fails on it.
- e2e `backups.spec.ts`, `people.spec.ts`, `access.spec.ts`, `0-design.spec.ts`: 148 of 149 passed; the one failure was a locator in the new step of `backups.spec.ts` that matched the restore form's code field too. It is scoped to the schedule form now and `backups.spec.ts` was run again: 4 of 4 passed. No design picture changed.
- Restore drill (`scripts/restore-drill.sh`, its own image tags): passed, with the backup service of this wave.

## Not proven

- `prune` in `backup-service.sh` has no automated test: the script runs its loop when sourced. It was checked by hand in WSL with a floor of 4, an unreadable file, a non-number and a floor of 0, and `shellcheck` passes. The restore drill runs the whole loop.
- That the server never reaches `./backups` rests on `compose.yaml`, which mounts it only into the backup service. A platform that mounts the folder into the server loses the backup service's own guard, not the console's.
- The console guard for a weaker rule rests on the server. Against code running in the server's own process only the backup service's guard holds, and only for backups.
- The first round after the upgrade holds the larger of the console's choice and the worker's defaults; an installation that kept fewer on purpose confirms once. This was not tried on an upgraded installation, only in tests.
