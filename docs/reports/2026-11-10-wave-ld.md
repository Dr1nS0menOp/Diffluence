# Wave LD: what a real server showed, 10 November 2026

Written for: a later build session. What the first stress test on a real server found, what this wave changed, the numbers before and after, and what is still to be measured. Spec 050 holds the plan and the reasons.

## Where it started

The stress test of 10 November ([report](2026-11-10-stress-test.md)) ran 5,000 seeded people on a server with 8 cores for PostgreSQL. PostgreSQL ran out of CPU from about 50 active people. Three queries took most of its time: file names in the quick box, the feed, and the count on the bell. Saving with all 5,000 at once waited 3.7 s on the audit lock. The install guide missed three things an operator needed.

This wave cherry-picks that report and its scripts (`scripts/stress/`), so they land with the fixes.

## What changed

### Connections

Code that held a connection, in a transaction or as a querier passed in, asked the pool for a second one in eleven places (spec 050 lists them). Under enough of the same work at once, every connection waits for a second that nobody frees. Each place now reads through the connection it holds. A request also waits at most 10 seconds for a connection and is then told "busy" with `Retry-After`; background work keeps waiting, because nobody is there to answer.

How it was found: a short script listed every call made while a transaction is held that does not pass the transaction on, and each hit was read. Calls into file storage, the outbox and context helpers were false hits. A deeper call chain can still hide one: the limit is what keeps that from stopping the instance.

The limit sits in the pool's acquire tracer: pgxpool calls `TraceAcquireStart` on the connection tracer and uses the context it returns for the wait, so `db.WithAcquireLimit` on a request's context bounds every wait without wrapping the pool. `TraceAcquireEnd` notes a wait that ran into the limit, and `internalError` and the session lookup turn that into 503.

| Test | Before | After |
|---|---|---|
| 12 spaces created at once, pool of 3 | Hung until the client gave up at 30 s; the ones that waited longest in admission got 503 | All 201 in 0.6 s |
| A request while every connection is held | Waits as long as they are held | 503 with `Retry-After` after 10 s |

### Queries

All three now ask the permission rule only about the few pages they could show, the way search and the tree already did (`search/words.go`, `pages/branches.go`).

Measured with `scripts/stress/bench-data.sql`, which fills an empty database in under a minute. The first try took the planner's word that new tables were empty (no statistics inside the transaction) and planned 15 billion row pairs; `ANALYZE` after the large inserts fixed it. A first set without a page tree made the bell look cheap at 1 ms, because `perm_hidden_pages` reads `page_tree`; with trees seven levels deep it cost 55 ms, matching the server's 80 ms under load.

| Query | Before | After |
|---|---|---|
| The feed, recent | 379 ms | 20 ms |
| The count on the bell | 55 ms | 5.8 ms |
| File names, a common word | 268 ms | 41 ms |
| File names, a rare word | 277 ms | 18 ms |
| File names, near a typo | 1,363 ms | 78 ms |
| The notification list (not changed) | 3.8 ms | |

The list of notifications was rewritten too, measured at 3.8 ms against 3.1 ms, and put back: not worth the extra text.

The feed's answer is proven the same: `TestTheFeedGivesWhatTheFormerQueryGave` keeps the former query in the test and compares, through the API and its cursor, for three people and all three tabs.

### Not changed: the audit lock

Every audited write holds the chain's lock until its commit is on disk, so audited writes go one at a time at the disk's sync rate. Shortening the lock means a new design of the chain (hashing after commit by one writer, for example), which changes what ADR-013 and ADR-039 promise. Not proven safe here, so it stays, and the install guide says what it costs and what helps.

### The install guide

- An IP address as `DIFFLUENCE_PUBLIC_URL` is refused at start, with the reason. It never worked: the passkey library refuses an address as RP ID, so the app stopped at start in a loop. Refusing was chosen over starting without passkeys, because passkeys are part of how login stays safe and a second way of running adds paths to test. `localhost` stays allowed.
- PostgreSQL memory settings by machine size, `pg_stat_statements` with `CREATE EXTENSION`, and the audit lock's cost on a slow disk.

## Gates

`make check` passed; `scripts/e2e` 452 passed and 7 skipped, with no picture changed; the full mutation check caught all 535. The run of the mutations for changed paths first found nine that no longer applied: seven older ones aimed at code this wave changed, and two new ones that did not compile. All were fixed before the full run.

## Not proven

- The load test with these changes on the server. Every number above is one query in a container.
- That no other place takes a second connection. The 10-second limit covers what the search missed.
- The audit lock on fast disks.
