# Wave AG: running the installation from the console

Report of 2026-11-11. Spec 058.

## What was asked

Manage as much as possible from the admin screen, backups first, the same on every platform; then decided the same evening: a full restore over the live installation from the console too.

## What the study found

Every command and setting is sorted in spec 058, section 1. Maintenance mode, the audit chain check and audit retention were already in the console. Most settings stay show-only, because a wrong value would make the console unreachable to correct it, or because they hold secrets that would otherwise land in every backup. The backup schedule is the one setting that moves to the console now.

## What is built

- Migration 0048: `backup_requests`, `backup_runs`, `backup_restore_checks`, `backup_worker`, `backup_mail`.
- `internal/backups`: the console and the worker meet in the database. The worker asks every minute, claims a request in the same transaction, and reports each backup with the step that failed.
- `diffluence backup next | report | restore-checked`, with the application role's database access the worker already has.
- The Compose backup service asks the console and reports; it falls back to its own schedule against an older release.
- `scripts/restore-check.sh` reports each weekly test restore.
- Console: Backups, Configuration (show only) and Sessions.
- System health: "the latest backup failed" and "the latest test restore failed".
- Mails to administrators on failure, from a server node, at most twice a day per kind.

## Decided during the wave

The decisions D1 to D12 are in spec 058. The main ones: the worker uses its database access, not an API token (D2), because a token fails exactly when the app is on its waiting page during an upgrade; failures are mailed by the server, not the worker (D6), because only the server holds the key that seals mail; a guided replacement of `master.key` is a later wave of its own (D11).

## Planned, not built

The restore over the live installation (spec 058, 3.2), decided by the product owner on 2026-11-11: too large and too dangerous to build beside the rest. The plan covers the fresh second factor, the typed confirmation, the safety backup, the worker behind the waiting page, the checks after, the trace in the restored audit log, the daily limit and Kubernetes.

## Not proven

- The backup service script against a real database in this wave's gates; its shell was checked with `bash -n`, and the commands it calls are tested in Go.
- A real mail reaching an administrator; the test checks what is queued.
