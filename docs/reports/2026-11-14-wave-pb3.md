# Wave PB3: draft and published spaces, approval releases

Builder report for spec 073, wave PB3. It covers what was built, what was measured, what was decided on the product owner's behalf, and what is not proven yet. The part stays experimental and off by default.

## What was built

**The mark.** A state of kind approved has an optional field, `release_when_approved`. The validator refuses it on any other kind and names the state. Setting or clearing it, in a save or a copy of a template, needs `space.administer` besides `space.workflows`; it is part of the definition, so each change is a new version of the workflow and is audited as `workflow.saved`. The workflow editor offers it on approved states of a draft space while the part is on; elsewhere it shows only on a state that carries it, with the note that it does nothing here.

**Approval releases.** The worker hands `page.version_approved` (of DC3) and `page.withdrawn` to the publishing module after the notifications, as it does for public sites. On an approval in a draft space whose approved state is marked, a run of that page is queued in the queue of the pair (a `release_runs` row with `actor_type` `approval`, no actor, `caused_by` the approver and the round in its options) and carried out by the same code as every run, without the approver's rights. Nothing is queued when the twin already has that text (a return to the approved text), when that version was queued before, or while the part is off. A run of the system leaves out a page with a view restriction in the draft. The twin version it writes has no person as its author, and its history says so; a twin it makes is owned by the person who made the pair, whom its byline names.

**Withdrawal.** A withdrawn page whose twin is published gets a take-off run by the workflow, with the withdrawer as the cause; the twin goes to the published space's trash. This happens in every pair, also while the part is off.

**What a release takes.** By hand and in runs, a controlled page goes at its approved version, read from the control row (`releaseVersion`), and each file it shows goes at the version and name that version pinned (DC3's `attachment_pins`), never a newer version uploaded for a change in review. A page never approved is skipped with its reason; the pages below it now go, placed under the nearest twin above, so a never-approved section or home page no longer keeps a controlled space out of a whole-space release. A released page with a newer version under review is Waiting for approval, on its band and on its tile.

**The pair's settings.** "Release pages under a workflow only by their approval": runs skip controlled pages ("left to approval"), and a person cannot release them, except an approved version whose approval release did not go. "Show readers who approved a page", off by default.

**What people see.** A twin of a controlled page shows "Approved <date> · version N", with the approver when the setting is on. A draft page whose approval release did not go shows why, in words. The approver and the authors since the last release get one notification, `approval_release`. The history names approval and withdrawal runs with the person who caused them. A controlled page in a draft space has one band: control first, then release.

**Verification.** `POST /pages/{id}/release/verify`, for those who see the audit of the draft space, on a draft page: the draft version must still hash as the release recorded, and the rewrite done again from the link map must give exactly the document the twin holds. The link map now also keeps the words of links that became text, the files and the keys of both spaces, so the rewrite is reproduced without reading anything that changed since. Each check is audited as `release.verified`.

**Data.** No migration. The mark and the two settings are optional JSON fields; runs of the system use the columns `actor_type` and `caused_by` that migration 0061 already had.

## Tests

Written before the code, failure paths first, and seen failing: `internal/workflow/release_test.go` did not compile before the field existed, and `internal/app/publishing_approval_test.go` failed with "has no twin", a 404, a 400 and a missing audit before the module followed the events. One test, a restricted page left to a person, was added after its code; its mutation is the proof that it can fail.

- `internal/app/publishing_approval_test.go`, 14 tests, among them a release of the approved version copying the file as that version pinned it after an author uploaded a new one: a failing approval release (published space archived) leaves the page approved, Changed since release, with the reason, and tells the approver; a never-approved version is refused by hand and skipped by a run, and a page in review goes at its approved version; withdrawal takes the twin off with and without the mark, audited as the workflow's; the leak test of PB1 for an approval release, with the approver's name absent until the pair shows approvers; the run's actor, cause, round and rights, Waiting for approval and its tile, a second approval, the returned text and an event handed over twice; a review that passes, and who is told; who may set the mark, its versions and audit, and a space in no pair; a whole-space release of a controlled space; only approval releases; workflows refused in the published space; verification, also of a twin changed past the database trigger; a restricted page left to a person; the measurement below.
- `internal/publishing/approval_test.go`: the version a release takes, the run's decision under only approval releases and which skipped pages keep the pages below them out, and over 300 random documents that the rewrite done again from the link map gives the same document, and differs without the page links.
- `internal/workflow/release_test.go`: the validator and the comparison of marks.
- `web/e2e/publishing.spec.ts`: the mark set in the editor, approval from the band releasing the page, the twin's approved line, withdrawal taking it off. `web/e2e/0-design.spec.ts`: two new pictures, `publishing-controlled-page` and `publishing-approved-twin`.

## Measurements

On the development toolbox, generated data, load average about 3.5 at the time:

| What | Without the mark | With the mark |
|---|---|---|
| The approval request itself | 13 to 16 ms | 13 to 15 ms |
| The work after it: events, and with the mark the run | 7 to 10 ms | 46 to 55 ms |

The approval request costs nothing more: the release reads the event afterwards. The release of one page by approval adds about 40 ms of background work, one run of one page as PB2 measured it. Not measured on the real-data dump or the server.

## Upgrade impact

No migration. The mark and the settings are new optional JSON fields the previous release ignores. Approval releases and withdrawal are handled by the worker of this release: a worker of the previous release handles the event without releasing, so finish upgrading every node that runs the worker before marking a state or withdrawing a released page. A page released before this release answers "cannot be verified" until its next release.

## Decided on the product owner's behalf on 2026-11-14

D39 to D51 in the decision table of spec 073, each "decided on the product owner's behalf on 2026-11-14, may be overruled": following the event instead of a hook in the approval; the mark read on the state the version was approved into, and nothing released twice; no person as author of a system run's version; restricted pages left to a person; approval waiting and withdrawal acting while the part is off; the exception for a failed approval release under only approval releases; the Waiting tile without a tab; pages below a page that cannot be released going; how verification works and what it does not compare; one notification type; who sets the mark; and where the approved-on date comes from. The spec's open questions were answered in PB2 (D36 to D38).

## Not proven, and not built

- **Not built:** signature manifestations (PUB-731) wait for DC4; the space-wide verification is PUB-920 in PB4; a stopped approval run cannot be resumed from the screen, it is released by hand instead; no tab lists the pages Waiting for approval.
- **Not proven:** a node of the previous release handling the event during an upgrade (it would release nothing; see Upgrade impact); approval while a larger run goes (PUB-1063: it queues behind it by the code of PB2, not tested on its own); an approval release meeting the limit of storage; notifications by mail and in the digest for `approval_release`; the approved-on line after a newer version was approved but not yet released (the date comes from the round, the name is left out); measurements on real data and the server.
