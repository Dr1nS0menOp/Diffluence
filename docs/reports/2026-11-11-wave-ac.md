# Wave AC: the audit chain sealed a moment after saving

Date: 2026-11-11. Spec 052, ADR-041, blueprint line ARC-203 (and ARC-237).

## Why

The first stress test on a real server (`2026-11-10-stress-test.md`) measured saves of 3.7 seconds (p50) and 6.9 seconds (p95) with all 5,000 people at once. Most of that was waiting for the one lock that every audited write took and held until its commit was on disk. The product owner agreed on 11 November to the way out that blueprint 04 already named: write the event without its hash, and let one worker chain it a moment later.

## What was built

- **Migration 0047** (expand only):
  - `audit_pending` for events that wait, with a trigger that lets a waiting event leave only once its copy is in the chain, and lets only its personal part be erased;
  - the view `audit_entries`, with every event, sealed or waiting.
- **Saving:** `audit.Record` writes to `audit_pending` in the same transaction as the change, and takes no lock.
- **Sealing:** `audit.SealWaiting` and `audit.SealIn` take the lock the chain always had, read up to 500 waiting events in the order they were written and became visible, link them, insert them into `audit_events` as every event was before, move their personal parts, and remove them from `audit_pending`, in one transaction.
- **Workers:**
  - every worker seals every second, and once more when it stops;
  - the console's check, `diffluence audit verify` and each checkpoint seal first.
- **Straight into the chain:** the upgrade marker and the note of a backup are written straight into the chain (`audit.RecordSealed`), because they run before migrations, when the database may be of the previous release.
- **Readers** see waiting events at once:
  - lists show them first, without a seq;
  - exports show them last, with an empty seq;
  - the console reads `audit_entries`.
- **Erasing a person** reaches the personal part of a waiting event, and cannot race the sealer.
- **Pruning** seals inside its own transaction, and the chain goes on from the anchor even when every event was removed.
- **Health and monitoring:**
  - System health has a line "Audit log": a warning after one minute of waiting, a call for a person after fifteen;
  - two new metrics and an alert.

## Measured

In the development container, with `TestMeasureSavesUnderTheChainLock` (32 writers, 1,280 saves, three runs):

| | Before | After |
|---|---|---|
| Saves a second | about 2,000 | about 17,000 |
| p50 | about 15 ms | about 1.4 ms |
| p95 | about 18 ms | about 2.8 ms |

That database does not sync to disk on commit. On the server the lock was held across exactly that sync, so the gain there is larger. The stress test has not been repeated.

## How it was proven

- **Failure paths first:**
  - a save while someone else holds the chain lock;
  - removing, emptying, rewriting, unprotecting or dropping a waiting event, also as the application role.
- **Order and concurrency:**
  - a transaction that began first and committed last is sealed last;
  - eight writers and two sealers at once give one chain with every event once;
  - a backlog of 503 events is sealed in steps.
- **Readers, erasing and pruning:** each has a test; see spec 052.
- **The worker's loop:** sealing every second, and sealing what is left when a worker stops.
- **Health:** the check, its thresholds and the metrics.
- **Older releases:** an event written straight into the chain, as the previous release does, joins the same chain. The upgrade tests run against the previous release's schema, which has no `audit_pending`, and pass.
- **Mutations:** 22 new, one for each new check.
  - The first full run missed one: without its lock, the sealer still passed the test with two sealers. Row locks alone already make two sealers that take the same rows wait for each other.
  - The lock is there for direct appends: the previous release and the upgrade marker. A new test holds the chain and shows the sealer waits and seals nothing.
  - The second full run caught all 606.
- **Gates:** `make check` passed. The browser tests ran 454 passed and 7 skipped.

## Decided during the wave

These are listed in spec 052, D1 to D7. The main ones:
- **D1, order:** the chain's order is the order events became visible.
- **D2, the lock:** one lock, the existing one, rather than a lease.
- **D5, the health line:** it reads the same whether nothing or a few events wait, so the console does not change every second.
- **D6, seq numbers:** they come from the identity column, so the previous release can append beside the sealer.

## Not proven

- **The server:** saves and sealing lag at 5,000 people. The stress test needs to run again.
- **Two machines:** a worker that dies while sealing, with another taking over on a second machine. It is covered by the transaction and the two-sealer test, but not tried with two real machines.
- **A rollback during an upgrade:** if an installation goes back to the previous release while events wait, they stay unsealed until it upgrades again. The changelog says so. The upgrade test's rollback step does not look at waiting events.

## Seen outside this wave
