## 2. Study and leak paths

How a task's permission follows its page is in spec 086, "Tasks". In short: `page_tasks` holds the tasks of the version readers see, and a task result passes `perm_visible_pages` at the moment of the search. Each way a hidden task could show was tested first:

| Path | Test |
|---|---|
| A task on a restricted page | `TestTaskSearchFollowsThePageOfTheTask` |
| A task on a controlled page never approved | same |
| A task only in the working version of an approved page | same; found by nobody until approved (D7) |
| A task on an archived page, a task in the trash | same; the archived one only when asked for |
| The total of a task search | same: a hidden task is not counted |
| A guest offered people outside the space in mentions and Share | `TestFieldsWithoutViewProfilesOfferOnlyPeopleOfTheSpace` |
| The box offering people without *view profiles* | same |
| The People tab showing people out of reach, or addresses | `TestThePeopleTabKeepsToWhomTheReaderMaySee` |

## 3. What was built

- **Server.** `identity.NameWords` turns typed text into word starts that cannot reach the syntax of a query; `Directory` (fields), `PeopleByName` (the box), `sharing.directory` (mentions and Share without *view profiles*) and `people.List` (the People screen and tab) use it. `Directory` reads an address only for text with an @. `search` gained `kind=task` with `Result.Task` (id, done, date, the assigned person's name), the same shape of query as comments, with the space words of the syntax and archived pages.
- **Migration 0075** builds `page_tasks_words_idx` alongside the tables.
- **The migration runner.** The first migration with `-- transaction: none` made `TestMigrateIsIdempotentAndConcurrentSafe` fail with a deadlock: nodes waiting in `pg_advisory_lock` hold a snapshot that `CREATE INDEX CONCURRENTLY` waits for. Waiting nodes now poll `pg_try_advisory_lock` every 100 ms; the grants after migrating poll `pg_try_advisory_xact_lock`. The test passed three runs in a row afterwards.
- **Screen.** `web/src/views/search.tsx`: a Tasks tab; the People tab from `/people` with picture or initials, name linked to the profile, job title and department; the Spaces tab with badges; `LoadingBox` and the screen of nothing found on all three; one hook for paged searches, shared with the content tab. `TaskMark` in `components/kind-mark.tsx`.

## 4. Load

People, on 20,000 generated people and 5,000 groups in the development database, PostgreSQL 16, `\timing` of three runs of a prepared statement:

| Query | Time |
|---|---|
| Old field query, any text (EXPLAIN ANALYZE) | 38 ms |
| Names, a rare start ("vrie") | 8.4 to 9.0 ms |
| Names, one letter ("j", a quarter of all names) | 10.7 to 15.1 ms |
| Names, two words ("jan vr") | 11.9 to 13.0 ms |
| The same with 500 groups instead of 5,000 | 1.6 to 1.8 ms |
| An address start ("person123@") | 6.6 to 12.0 ms |

Most of the cost with 5,000 groups is reading their names; an index for group names and one for addresses were tried and brought each search under 5 ms, but each would have been a migration of its own (one statement per migration that builds alongside), so they were left out (spec 086, "Data").

Tasks: the request costs 10 queries (`TestTheMainScreensStayWithinTheirQueryBudget`). The run of `TestSearchOnRealData`, which now also times tasks, a field for people and the People tab on the seeded dump, is reported in section 6.

## 6. Real data

`TestSearchOnRealData` on the seeded dump (60,385 pages, 5,002 people, 121 groups, and no tasks at all), on the build VM at a load of 16 to 40, median of seven through the whole application:

| Search | Time |
|---|---|
| The ten searches of spec 080 | 317 ms to 2.25 s, all over the 100 ms budget, as in SR1 on the loaded VM |
| Tasks | 17 ms (the dump holds no tasks, so this proves only the empty path) |
| A field for people, "per" | 32 ms |
| The People tab, "per" | 1.24 s |

The test fails on the budget for every search, old and new, so these numbers compare nothing with capacity. Two things stand out and are not proven either way: the People tab, which is the query of spec 013 (`perm_visible_people` and a count) with the index of names instead of a read of every name, took 1.24 s for a start that matches nearly every person; and the time to build the index of tasks could not be measured, because the dump has no tasks.
