# Wave O1: it watches itself

Date: 2026-11-10. Spec: [051](../specs/051-it-watches-itself.md). Wave 1 of [spec 048](../specs/048-study-of-07-and-08.md). Lines OPS-077, OPS-089, OPS-090 and OPS-103 to OPS-107.

## What was built

- **Health rules** (`internal/health`): one pure function from facts to eight checks (disk, database, backup, migrations, background work, mail, login, release), each `ok`, `warn` or `problem`, with a code, its values, and an English sentence for the command line. The thresholds are named constants: 10% and 2% free disk, 26 hours for a backup, a day for a waiting contract migration, 60 days for a release, and a month of growth against the free disk.
- **The guard** (`storage.Guarded`): wraps the store and refuses every new file below 2% free with the new error kind `no_room` (HTTP 507), reading the disk at most every 30 seconds. Reading, removing and listing files never wait for it. Text lives in the database, so it saves.
- **Facts** (`app.ReadHealthFacts`): one `statfs`, one statement for counts, the last backup, the last migration and the size samples, and the existing migration state; kept 30 seconds per node.
- **API**: `GET /api/v1/admin/health` for administrators; `/readyz` stays `200` and adds `"notes": ["disk_low"]` from the guard's cached reading, so a probe never waits for the database; System health gains the build date.
- **Size samples and cleaners**: migration 0046 adds `database_size_samples`. The worker measures the database hourly and cleans daily: finished jobs and sent mail after 30 days, failed ones after 90, nodes that stopped without leaving after a day, samples after 40 days.
- **Metrics**: disk free and total, database size, backup time, last migration time, build time, events that gave up, the stuck outbox, failed mail, and how many checks need a look or a person. The latency histogram gains a bound at 0.3 seconds, the latency objective.
- **Build date**: `version.Date` from the commit date, set by `make build` and the image's `BUILD_DATE`.
- **`diffluence doctor`**: configuration, the health checks and a shallow key check, printed without addresses or secrets; exits 1 on a problem.
- **Console**: System health starts with the checks; a band on every console page while the disk runs out; the summary lists the checks that need a look, without repeating the disk or the missing mail server.
- **Monitoring files**: `deploy/monitoring/diffluence-rules.yml` (SLOs with burn-rate alerts and alerts for causes) and `diffluence-dashboard.json`, with a test that every metric they name is one the server sends.
- **Guide**: `docs/operations/monitoring.md` lists the checks, every metric, the alerts and everything that grows with its cleaner. The release checklist passes the build date.

## Decided during the wave

- `/readyz` stays ready on a full disk (spec 051 D5): one node saying "not ready" would stop text too.
- The note on `/readyz` comes from the guard, not from the health facts, so a probe never waits for the database when the pool is busy.
- The identity provider is not asked whether it answers: that would call an outside server on every look. The login check shows accounts whose password login stopped.
- The summary leaves out the disk check (the band and its own line say it) and a missing mail server (it has its own line).
- The latency histogram gained a bound at 0.3 seconds, so the 300 ms objective is measured, not estimated from 0.25 or 0.5.
- `doctor` says "the database does not answer" without the error of the driver, which names the host and the user.

## Not proven

- The rules were not loaded into a running Prometheus, and the dashboard not opened in Grafana; the test only checks the metric names. That is for the test machine (spec 048, wave 7).
- A disk that really fills: the tests stand in for one with a fixed reading.
- The opt-in check of the public release feed (OPS-106) is not built: nothing phones home.
- `config check` (OPS-100) is still its own line; `doctor` only loads the configuration.
