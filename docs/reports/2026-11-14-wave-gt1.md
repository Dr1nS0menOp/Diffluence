# Wave GT1: guided templates, the model, versions and the all-or-nothing set

Builder report for spec 074, wave GT1. The study is `docs/blueprint/09-enterprise/templates/`; the decisions taken while building are TPL-1425 to TPL-1440 in the spec's decision table.

## What was built

**The model.** A template is a list of entries. The first is the page that was always the template's text (`templates.page_id`, key `root`); every other entry is a page or a folder with its own hidden page of kind `template` (`template_entry_pages`), its title pattern, labels, restrictions and workflow. A **manifest** (`internal/templates/manifest.go`) describes what one version makes and pins the page version of each entry's text. Its validator checks one root first, unique keys, no loop, at most 100 entries and 6 levels; the texts together hold at most 40 distinct questions and 5 MiB, and every link to an entry points at one that exists. A manifest is at most 64 KiB, checked in Go and by the column's `CHECK`.

**Versions.** `template_versions` holds every version; each save that changes what the template makes is the next version, and a change of name, description or category is not (TPL-600). Every version is approved at once in this wave, as managers publish their own templates (TPL-1411); approval comes in GT4. A form is bound to the version it showed (`version` in the request, TPL-603). A plain template that the previous release changed, which writes no version, gets its next version on first read, from its row and text (TPL-1103).

**Making a set** (`internal/templates/sets.go`). `MakeSet` and `CheckSet` share `prepare`, which:
- loads the version;
- checks every right the set needs and refuses the whole set, naming every entry and the right it lacks (TPL-810);
- checks the place (TPL-800 to TPL-804) and the room for files (TPL-103);
- works out every page with its id made beforehand (TPL-111), its title (TPL-140 to TPL-142) and its text, with the answers as text and the values of the template in place.

The real run is one transaction under the tree lock of the space:
- the row of the set first, so a request sent twice waits and gets the first set (TPL-123);
- then each page with its files, draft or first version, labels, workflow and restrictions;
- then the origin rows in one statement;
- then the removal of the empty page that was waiting (TPL-122, which fixes TPL-006);
- then the audit event.

A set stops after 60 seconds (TPL-826). `pages.StartFromTemplate` is gone: `Use`, the automation action and the new route all go through `MakeSet`, so there is one path.

**Background sets.** A set of more than 25 pages is a job (`template_set`). The job checks every right again, takes one slot of its person and one of two slots of its space with session advisory locks, or goes back to the queue (`jobs.ErrNotYet`, which rests a job for a second so nothing spins or waits behind it). It writes `template.set_failed` after a rollback. It drops its answers when it ends, unless its worker stopped, when a retry needs them (TPL-1434).

**Stored copies** (TPL-821). `attachments.CopyAll` remembers each new object key in `pending_file_copies` on its own connection before it stores the file, and the copying transaction forgets it on commit. The task `collect-pending-copies` hands keys older than an hour that no file version refers to over to `storage_deletions`. This also closes the gap for the one-page templates of before.

**The document.** The inline block `templateValue` (sources `date`, `space`, `creator`, `set`, `template`, `entry:<key>`) is accepted by `Normalize`, filled in when a set is made, and refused in any page that is not a template, both in a draft and when published (`checkDocumentKind`, `ForPublish`).

**The switch.** `guided_templates` is a new experimental part, off by default. Every new route answers 404 `experimental_off` while it is off. A guided template is left out of the gallery and its use answers the same. Turning it on is refused while a live node knows fewer migrations (TPL-1103, TPL-1428).

**The screens.** The template editor shows a minimal list, "Pages this template makes", while the part is on: add a page below another, write its text in the same editor, remove it, and publish the pages as they are made. The managers' list marks a guided template "needs guided templates" while the part is off. The gallery sends the empty page to the server instead of deleting it in a second call, and binds a guided template to its version and to a one-time request key. A background set shows a status note.

**Migration** `0060_guided_templates` (expand), after 0058 of DC2 and 0059 of EV2. It adds:
- `template_versions`, `template_entry_pages`, `template_sets`, `page_template_origin` and `pending_file_copies`;
- `owner_id`, `state`, `approved_version` and `guided` on `templates`;
- an approved version 1 for every template.

Each new table has its owner in `internal/db/boundary_list_test.go`. `internal/attachments` now names `storage_deletions` six times instead of five.

## Measurements

Measured on generated data in the development containers of a loaded Windows machine (WSL), outside the race detector: `DIFFLUENCE_LOAD_BUDGET=1 go test ./internal/app/ -run 'TestASinglePageFromATemplateCostsWhatItDidBefore|TestTheLoadBudgetOfASet' -v`. The real-data dump of wave PF that TPL-1422 asks for was not at hand, so these are not the measurements the spec wants; they show the order of size.

| Budget | Spec | Measured (three runs) |
|---|---|---|
| A set of 10 pages, p95 of 40 | 300 ms (TPL-901) | 124, 130, 136 ms; median 104 to 109 ms |
| A set of 100 pages as background work, p95 of 7, from claiming the job to done | 3 s (TPL-901) | 1.00, 1.00, 1.15 s; median 0.85 to 0.92 s |
| The audit queue empty after a 100-page set | 5 s (TPL-903) | at most 0.24 to 0.27 s of sealing, plus the one-second tick |
| One page from a template, against today | within 10% (TPL-901) | see below |

**One page against today.** Each set writes more than one page from a template did: the row of the set, the origin row, and the audit and outbox event of the set. The first version of the code also did avoidable work and was about 13% slower, measured by running main (`ef029b8`) and this branch alternately, four rounds each, 31 uses per round. The avoidable work was:
- a transaction and a row lock on every use;
- reading the texts twice;
- checking rights that no entry needed;
- looking up existing titles that only the check step shows;
- `spaces.Get`, which costs about seven queries for a name.

Now only a template owed a version takes a lock (TPL-1103). Rights are asked only when an entry needs them, and existing titles only for the check step. The space name comes from the new `spaces.Name`, and the date with the template's own row. Measured again alternately, the medians of main were 19.3, 15.8, 19.0 and 21.2 ms and those of this branch 18.5, 17.5, 16.8 and 20.4 ms: no difference this machine can tell apart. The machine was loaded by other builders throughout, so single rounds vary by a quarter.

**Writes are not batched per table** (TPL-901 asks for that): each page still goes through the same insert, draft and label code as any page. The budgets hold without it, so it was left for when a measurement on the real-data dump says otherwise.

## What was not proven

- The budgets on the real-data dump (TPL-1422), and the gallery budget of TPL-900, which belongs to GT4.
- The bell for a background set (TPL-121, decided as TPL-1433).
- "Publish all" on the root of a set of drafts (TPL-150).
- The check step in the form (GT2). The dry run is there as `POST /templates/{id}/sets/check` and refuses exactly as the real run.
- Setting restrictions and workflows of an entry from the screen. The API takes them, and the tests use it.
- Inserting a value of the template or a link to a page of the set from `/` in the editor (TPL-110, TPL-211). The editor shows and keeps such a block, but only the API puts one in. This comes with the editor sections of GT2.
- A space under document control with a set published at once (TPL-151, the controlled case): the code path is `appendVersion`, as for any published page, but no test of a set in a controlled space was written.
- The N/N+1 upgrade test with the previous binary. The fallback of TPL-1103 is tested by changing the row as the previous release would. The migration is tested by removing what it adds and running it again.
- The renaming of a field across entries and conditions (TPL-230), which needs the editor sections of GT2.

## Gates

- **Targeted mutation check** (`MUTATION_CHANGED` listing `internal/templates`, `internal/document`, `internal/spaces` and `internal/example`, `MUTATION_JOBS=2`), on the tree rebased onto main `18800f1`: 51 run, 51 caught. Of these, 19 are new for GT1, and the template-file mutation was brought up to date. The other new one, "any file comes through a template", lives in `internal/attachments`, which this run did not cover.
- **E2e** `0-design.spec.ts`, `organising.spec.ts` and `create-kinds.spec.ts`, on the same tree: 137 passed. One new picture, `template-pages.png`, looked at: the pages in tree order, indented with the tree's own token, rows as in every table of the app. `template.png` is unchanged, because the list sits below the template's editor.
- **`make check`:** passed on the same tree. Earlier runs stopped at the 20-minute limit of `internal/app` under the race detector. Both shared the machine with this wave's own e2e and mutation runs and other builders' mutation runs; every other package passed. The new tests first cost several minutes of that package, because each save of a template read every entry's text with a query of its own. The texts are now read in one query, and the 23 new tests of the package take about 67 seconds together under the race detector.
Found and fixed while running the gates:
- The console's list of experimental parts showed the key `experimental.part_guided_templates` instead of words. The strings check does not see keys built at run time, so the label is now in `en.json`.
- In `create-kinds.spec.ts`, clicking "Databases on" scrolls the page. With the two new rows of experimental parts (`publishing` of PB1 and this one), the Analytics row of the table above then sat under the sticky top bar, and axe measured its boxes against the search field (22.2 px of free space instead of 24). At rest nothing overlaps. The test now scrolls back before it checks, and says why.
- Every background set failed before it began, because a Go `int` was bound to a `text` parameter of the advisory lock of a space. The tests of TPL-121 and TPL-827 found it.
- `withRow` changed the newest manifest it was compared with, so the version owed after a save by the previous release (TPL-1103) was never made. Its test found that; a mutation keeps it found.
