# Report: wave O3, backups that run and restore (2026-11-11)

Spec 054, ADR-042, wave 3 of spec 048. Lines OPS-079 to OPS-082, and the follow-up of an installation that got stuck in the backup refusal of ADR-040.

## What was built

1. **A backup service in `compose.yaml`, on by default.**
   - It makes a backup every 4 hours, keeps the newest 42, and notes each one.
   - The image is a stage of the main `Dockerfile`: `postgres:16` with `gnupg` and the `diffluence` binary of the same build.
   - **Refusals:** it makes no backup without a key, and none when the key folder is the backup folder.
   - **Partial backups:** a backup is written under `.partial-` and renamed when complete.
   - **Ownership:** each backup belongs to the owner of the backup folder.
   - `scripts/setup-secrets.sh` makes the key and the folder.
2. **A node that waits instead of looping.**
   - When the checks before an upgrade refuse, `diffluence serve` keeps the address. `/livez` answers 200, `/readyz` 503 with the kinds of problem, and the API 503 with `Retry-After`.
   - Every other path gets a public page with the kinds and the commands that fix them, and no figures or dates.
   - It touches no data, and tries again every minute or on SIGHUP.
   - `diffluence healthcheck` prints the reason.
3. **The first upgrade without any backup goes on once**, with a warning and `system.upgrade_without_backup` in the audit log.
4. **`diffluence migrate` asks for the backup.** It used to check nothing. `--without-backup` goes on once and records it.
5. **`backup.sh` while the node is down.** It finds a stopped node's volume (`ps -aq`, found by the drill), notes through a one-off container, and sends SIGHUP to an unhealthy node.
6. **The weekly restore check.** `scripts/restore-check.sh` restores the newest backup into a throw-away project, checks it, counts, times it and removes it. The guide gives a systemd timer and a cron line.
7. **The guide.** It covers the backup service and copying off the machine, pgBackRest with point-in-time recovery and its two alerts, and why a standby is not a backup (3-2-1).

## Decided during the wave

- **On by default:** the service runs without a profile, because a rule that asks for a backup must come with one (D1).
- **One Dockerfile:** the image is a stage of the main `Dockerfile`, so there is one build and the binary that notes the backup is the same one (D2).
- **No figures on the public page:** it names kinds and commands, never free space or backup dates (D3).
- **The waiver is kept in the audit log**, where the backup notes are (D4).
- **`migrate` checks the backup**, because otherwise it was a silent way around the rule (D5).
- **Capabilities:** the service runs as root with only `DAC_OVERRIDE` and `CHOWN`, to read `master.key` (mode 600, owned by the app) and to hand the backup to the folder's owner (D6).
- **Signals:** `backup.sh` signals only an unhealthy node, because a release before this one stops on SIGHUP.
- **No signal from the service:** the backup service cannot signal the node, as it has no Docker socket, which it should not have. The node's minute retry covers it.

## Not proven

- pgBackRest and point-in-time recovery: written, not run (wave 7).
- The time a large restore takes (OPS-078, wave 7).
- The waiting page behind a real proxy and in a real browser.
- A timer that really alerts a person: the guide's units are not run here, but the script's exit code is tested.
