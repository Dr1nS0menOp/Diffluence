# Report: wave RV3b, migrations, checkpoint signing and restore orders in the backup service (13 November 2026)

## What happened

Wave RV3b builds spec 070. It moves three duties from the server to the backup service of `compose.yaml`, which already held the owner of the tables:

- the migrations of a new release, expand and contract;
- the signing of the audit checkpoints;
- the decision to carry out a restore asked for in the console.

The server's container now holds only the application role. The spec sets out the options for each part; ADR-044 records the decision.

## What was built

- **Migrations.**
  - `compose.yaml` gives the server only `database_url` and `DIFFLUENCE_MIGRATE_ON_START: "false"`. The backup service gets `DIFFLUENCE_UPGRADE_BACKUP_MAX_AGE` and `DIFFLUENCE_CONTRACT_GRACE`.
  - A node that does not migrate refuses a database whose expand migrations of its release have not run. It waits on the page of spec 054 with the new kind `migrations`, names the backup too when that is what the migration waits for, and looks again every 5 seconds while it waits only for the migration.
  - `app.TendSchema`, run as `diffluence worker migrate` every round of the backup service: the backup part of the checks before an upgrade and the upgrade marker, the migrations, the session defaults, the grants of the application role; then the contract migrations by the rule the server's worker used, recorded as `system.contract_migrated`.
  - The rule for contract migrations is one function, `contractDue`, for both places. A node without the owner and without migration on start runs none (`config.LeavesMigrations`).
  - `diffluence migrate`, `audit prune` and the restore runner name the backup service when the container has no owner. `user create-admin` waits for the migrations instead of trying them as the application role. `scripts/restore.sh` migrates a restored backup of an older release in a one-off container.
- **Checkpoints.**
  - `keys.Worker` derives, with HKDF from the backup key, the checkpoint key of the backup service and the MAC keys of the restore codes and seals.
  - Migration 0055 adds `audit_signing_keys`: each key after the installation's own, from a position of the chain, endorsed by the installation's key. A trigger on `audit_checkpoints` refuses a checkpoint of a key no longer in force. The application role may only read the table.
  - `audit.ChangeKey` makes the change point under the lock of the chain, and records `audit.checkpoint_key_changed`. `audit.WorkerCheckpoint` is the round of the backup service: change when needed, then sign when five minutes passed.
  - Verification, the witness comparison and prune anchors follow the key in force at each position, with only the installation's public key as input. `diffluence worker checkpoint` writes each witness line to the backup service's log.
  - The server's checkpoint job stops by itself once a newer key is in force.
- **Restore orders.**
  - `restore.Gate`: a 10-digit code from an HMAC over the restore's id and backup name, and seals on a confirmed restore and on the safety backup.
  - `restore.Claim` writes the code to the backup service's log once, through the line `code <backup> <code> <minutes>` of `diffluence backup next`. It compares the code the console stored in constant time; three wrong codes, or none in 30 minutes, end the restore. Every step is recorded.
  - The runner checks the seal before preparing, before the safety backup's result and before restoring. The way back checks the seal of the safety backup.
  - `POST /api/v1/admin/backups/restore/code` stores the code typed in the console, for system administrators. The Backups page shows the field once the code is in the log, and how many tries are left.
  - `diffluence backup restore-request` run inside the backup service holds the key and fills the code in itself.
- **Wording.** ADR-044; the threat model has rows for the audit log against the server's own process and for the restore from the console; `risks.md`, `install.md`, `upgrade.md`, `backup-restore.md`, `.env.example` and the changelog describe the new behaviour.
- **With wave RV3a.** The wave was brought onto main after RV3a landed. Restore from the console is an experimental part there, off by default; the route that takes the code stays open while it is off, as cancelling does, so a request made before the part was turned off can still be confirmed or end by itself. The threat model's table of what each control holds against now says what holds against a compromised app process for the restore and the audit chain, and its accepted risk about the owner password is narrowed to the layouts outside Compose.

## Gates

All on the tree brought onto main after wave RV3a:

- **`make check`** passes: formatting, vet, staticcheck, govulncheck, licences, the web and collab checks, and every Go test with the race detector. shellcheck finds nothing new in the three changed shell scripts; its four warnings in `restore-drill.sh` are on main as well.
- **The targeted mutation check** (`MUTATION_JOBS=2`, the changed files of `internal/keys`, `internal/audit`, `internal/restore`, `internal/config` and `cmd/diffluence`) ran 101 mutations and caught all of them, among them 19 of the 22 new ones; the other three mutate `internal/app`.
  - The first run found four of the new and changed expressions BROKEN: each left a variable unused, so the mutant did not compile. They were rewritten to keep the variable, and the second run caught all four.
  - Those three, and one more of `internal/app`, cannot be selected in the targeted mode without selecting everything. They were run by hand in the same way as `run_go` does it, and all were caught: an unmigrated database served, contract migrations in a server without the owner, the grace ignored, the server's checkpoint job failing once the backup service signs.
- **The e2e** of the backups page and `0-design.spec.ts`: 100 passed. No picture changed. A first run after bringing the wave onto main failed before its first test: the changed `compose.dev.yaml` of wave RV3a made the script recreate the database container after the server had prepared its database. The rerun passed
- **The restore drill** passes end to end on its own image tags, `diffluence:drill-<pid>` and `diffluence-backup:drill-<pid>`, in about 100 seconds. Its new steps:
  - the server's container holds no owner address;
  - the backup service migrates before the server starts;
  - a request written straight into `ops.restores` by the application role is refused and recorded;
  - a request of the server's container waits for the code, and the code read from `docker compose logs backup` is entered over the API, after one wrong code that is counted;
  - the restore and the way back run through requests made inside the backup service.

## Load

As the spec says: the backup service makes two indexed reads a minute for migrations, one read of the newest checkpoint, a signature every five minutes when something happened, and the restore query it already ran. The server reads the newest row of `audit_signing_keys` every five minutes. The trigger costs one indexed lookup in a table of a handful of rows per checkpoint. No change to saving, reading or search.

## Decided on the product owner's behalf on 2026-11-13, may be overruled

The decisions D1 to D10 of spec 070, in short:

- the backup service migrates, not a one-shot service;
- Compose only in this wave; Helm, the LXC script and the packages keep one process with both addresses;
- an old `compose.yaml` keeps working, with a line in the log at each upgrade;
- the checkpoint key, the restore codes and the seals are derived from the backup key;
- a chain of keys endorsed by the installation's key, with a trigger that refuses a key no longer in force;
- a code of 10 digits, 30 minutes, 3 tries;
- the threat model states plainly what holds against which holder;
- ADR-044, leaving ADR-043 to wave RV3a.

Two more, made while building:

- **The worker's rounds stay a minute apart also when the console cannot be asked** (an older database during an upgrade): `backup-service.sh` no longer sleeps the whole interval after a backup in that case, so migrations and checkpoints do not wait four hours.
- **A forged failure is not closed by the way back.** It is refused and recorded, and the nodes keep waiting, because closing it would let them serve on a database whose state nobody looked at. The message names `scripts/restore.sh`.

## Not proven here

- **The code field on the Backups page in a browser.** The e2e server has no backup service and no complete backup, so no request reaches the state where the field shows. The route behind it is tested, and the drill enters the code over the same route.
- **Helm, the LXC script and the packages.** They keep one process with both addresses, unchanged; their split is a later wave.
- **An upgrade of a real installation from the previous release to this one**, with its own `compose.yaml` and with the repository's. The tests cover both layouts against one database, and the drill a new installation.
- **A key change after the backup key is replaced.** Covered in the tests by a second key, not on a real installation.
- **Two backup services at once.** Compose runs one; two would take turns on the migration lock and the chain lock, but that was not run.

Seen on the way, not changed: in the drill, `scripts/restore-check.sh` reports "the console could not be told the result", because the folder it tells from is not the drill's Compose project. That is so on main as well.

## Upgrade

What an operator does is in `docs/operations/upgrade.md`, "Upgrading to the layout of spec 070": with the `compose.yaml` of the repository, rebuild the backup service with the server (`docker compose up -d --build`); with a `compose.yaml` of one's own, nothing breaks, and three lines move the owner to the backup service.
