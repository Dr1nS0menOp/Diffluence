# Wave RV12: who a rule runs as

Builder report for spec 092. It covers what was looked at, built and proven.

## What was looked at

- `automation.Service.Update`: who may change a rule, and which account a saved rule acts as.
- `perform` and `Test` in `internal/automation/run.go`: when conditions are judged, and as whom a test run reads pages.
- `find` and `preview`: which account a lookup and the permission of a test step use.
- `Definition.Problems`: what keeps a rule from being switched on (PLT-077, PLT-078).
- Blueprint 03 chapter 12, PLT-082 and PLT-083, and spec 015 D10, D11.

## What changed

- **Holder.** `holds` says whether the caller holds a rule: the person it acts as, or its owner while that owner may still lend its service account (`mayLend`, split out of `account`). `Update` sends the holder to `change`, someone else with `take_over` to `takeOver`, and anyone else to `switchOff`, which takes only the same name and definition with `enabled: false` and answers `409 rule_held` to anything else.
- **Take-over.** `takeOver` sets owner and account to the caller (or a service account they may lend), switches the rule off, ends the pause, deletes the incoming webhook address, records `rule.taken_over` with `from_owner` and `from_account`, and notifies the previous owner and account (`tellPreviousHolders`, through the existing `tellOwner`).
- **Saves that cross.** `change` and `takeOver` update the row only while it still has the owner and account that were read; otherwise `409 rule_changed`.
- **Test runs.** `Test` runs as the caller unless the caller holds the rule. `find` and `preview` use the caller of the run instead of the column of the rule, so a test and a real run read the same way.
- **Conditions need a page.** `cannotJudge` makes `perform` and `Test` answer `conditions_need_page` for a rule with conditions and a run without a page, before anything else is looked at. `Problems` adds a problem on the conditions (step -2) when the trigger brings no page.
- **Texts.** `rules2.outcome_conditions_need_page` and `rules2.report_conditions_need_page`.
- No migration, no new route; `Input` gains `take_over`.

## How the tests prove it

| Test | Proves |
|---|---|
| `TestSomeoneWhoDoesNotHoldARuleCannotChangeWhatItDoes` | Another space administrator cannot change the actions, the name or the account (`409 rule_held`); the rule is unchanged; the holder still changes it |
| `TestSomeoneWhoDoesNotHoldARuleCanSwitchItOffAndDeleteIt` | They switch it off without taking it over, cannot switch it on again, and can delete it |
| `TestATakeOverMakesTheRuleActAsWhoeverTookItOver` | Owner and account become the taker, the rule is off and has no address, one audit entry names the taker and the previous owner, the previous owner is notified, and afterwards the previous owner gets `409` |
| `TestARuleTakenOverRunsWithTheRightsOfWhoeverTookItOver` | After the take-over a run cannot see a page only the previous holder may see (`not_visible`) |
| `TestATestRunBySomeoneElseReadsPagesAsThem` | Find pages finds a restricted page for the holder and not for someone else; a test on that page by someone else is `not_visible` |
| `TestATestRunBySomeoneElseSaysWhatTheyMayNotDo` | A step of a test by someone who only reads says `account_may_not`, while the holder's says it would run |
| `TestAnInstanceRuleIsChangedOnlyByItsHolder` | The same among administrators for a rule of the instance, and the take-over |
| `TestTheAdministratorWhoChoseAServiceAccountHoldsTheRule` | The administrator who chose a service account holds the rule; another manager does not; the owner who lost administrator does not either |
| `TestConditionsUnderATriggerWithoutAPageKeepARuleOff` | Such a rule cannot be created switched on, and switched off it has one problem, on its conditions |
| `TestARunWithoutAPageDoesNothingWhenTheRuleHasConditions` | A rule of that shape stored by an earlier release labels nothing, its run is skipped with `conditions_need_page`, and a test run says the same |
| `TestConditionsNeedATriggerThatBringsAPage` (`internal/automation`) | The problem for schedule, incoming, group and space triggers, and none for manual and page triggers |

## Decisions taken on the product owner's behalf, may be overruled

- RV12-1 (spec 092 D1, D2): only the holder changes a rule or switches it on; others who manage it may switch it off and delete it. Renaming counts as a change.
- RV12-2 (D3): a take-over is explicit, `take_over: true` on the existing route; the rule starts off, its incoming address ends, the previous holder is told, and it is audited. The reason PLT-083 asks for is not built.
- RV12-3 (D4): a test run runs as the caller, unless the caller holds the rule.
- RV12-4 (D5): a condition that cannot be judged does not hold; conditions under a trigger without a page are a problem on the rule. A Find pages step does not give conditions a page.
- RV12-5: the holder of a service-account rule is its owner only while that owner is an administrator, the same test as choosing the account.
- RV12-6: no migration. Who took a rule over and when is in the audit log and in `owner_id`; a column would add nothing a reader needs today.

## Changed test

`TestATestRunChangesNothingAndSaysWhatTheAccountMayNotDo` (spec 015) proved that a test run says what the rule's account may not do by pointing the account at another person. Under D4 the owner no longer holds such a rule, so the test now points it at a service account with read rights only, which the owner, an administrator, holds.

## Not proven

- The guard against two saves crossing (`409 rule_changed`) has no test that makes two saves meet; it is a `WHERE` on the owner and account read.
- During a rolling upgrade a node of the previous release still accepts changes from someone who does not hold a rule.
